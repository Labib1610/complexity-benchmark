# Problem C — Telemetry Window: Diagnostic Code

Time limit: 2 s   Memory limit: 256 MB

## Description

An orbital satellite is scheduled to execute **j** observation jobs before it passes out of communication range in exactly **T** milliseconds.

Each observation job requires two sequential phases:
1. First, the targeting gimbal (Subsystem 1) must orient to the correct coordinates. For a given job, this takes **p1** milliseconds.
2. Afterward, the imaging sensor (Subsystem 2) must expose the frame. For a given job, this takes **p2** milliseconds.

The satellite's hardware constraints dictate that:
- The targeting gimbal can only orient for one job at a time.
- The imaging sensor can only expose for one job at a time.
- For any given job, the imaging sensor cannot begin its exposure until the gimbal has completely finished orienting for that specific job.

Mission control has determined that completing all **j** jobs within the **T** millisecond window is impossible, regardless of the execution order. Your task is not to attempt a schedule, but to output a directly checkable diagnostic code proving why the sequence cannot be completed. 

You must output a certificate identifying a structural bottleneck. The certificate must be exactly one of the following formats:
- `JOB i` : Denotes that observation job **i** (1-based) is a bottleneck. This applies if the inherent sequential progression through both subsystems for this specific job alone requires more time than the window allows.
- `LOAD c` : Denotes that Subsystem **c** (**c** $\in \{1, 2\}$) is a bottleneck. This applies if the serial operation of Subsystem **c** causes its aggregated active time across all **j** jobs to exceed the window, ignoring all other pipeline dependencies.

It is guaranteed that for the provided data, the deadline is impossible and at least one such bottleneck condition holds. If multiple jobs or subsystems satisfy the criteria for a diagnostic code, any valid code proving impossibility is acceptable.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the orientation time on Subsystem 1 and the exposure time on Subsystem 2 for that observation job.

## Output

Print a single line containing one valid diagnostic code: either `JOB i` for a bottleneck observation job, or `LOAD c` for an overloaded subsystem.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, observation job 1 requires 70 milliseconds of orientation followed by 60 milliseconds of exposure. Since this sequential dependency inherently requires more than 100 milliseconds, `JOB 1` proves the window is impossible. 
In Example 2, no individual job's sequential progression exceeds 150 milliseconds. However, Subsystem 1 must operate serially for 50+50+50+50 = 200 milliseconds in total. Since this exceeds the 150 millisecond window, `LOAD 1` is a valid diagnostic code.

The explicit inequalities (`p1 + p2 > T`, `sum1 > T`, `sum2 > T`) were removed from the general description. Instead, the problem describes the physical bottlenecks ("inherent sequential progression... for this specific job alone" and "aggregated active time across all j jobs"). This forces the model to derive the mathematical bounds from the hardware constraints rather than matching the explicitly provided formulas. Furthermore, the uniqueness constraint from the previous attempt was corrected to explicitly allow any valid diagnostic code if multiple bottlenecks exist, restoring the exact acceptance criteria of the seed.
</RATIONALE>
<PRESERVED_ANSWER>
The conditions for outputting `JOB i` or `LOAD c` mathematically translate exactly to `p1 + p2 > T` and `sum(p_c) > T`, meaning the valid set of output certificates for any given input is identical to the seed.
</PRESERVED_ANSWER>
