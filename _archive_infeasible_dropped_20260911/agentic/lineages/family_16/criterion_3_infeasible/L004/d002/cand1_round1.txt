# Problem C — Impossible Deadline: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A factory processes **j** jobs through exactly **two** machines. Every job is processed on machine 1 first and then on machine 2. For each job you are given its processing time on machine 1 and on machine 2. Each machine processes only one job at a time, and a job reaches machine 2 only after finishing on machine 1.

There is a required deadline **T**: every job must be completely finished by time **T**. In general, finding a valid schedule requires evaluating the **j!** possible job orderings to see if any permutation avoids delaying jobs past the deadline.

Your task is to evaluate the scheduling requirements and determine whether a valid job ordering can meet the deadline. If no sequence among the **j!** possibilities can successfully finish all jobs by time **T**, you must output a short certificate proving that the deadline is impossible. 

A valid certificate of impossibility must take one of the following forms:

- `JOB i` — where **i** (1-based) is the index of a specific job that inherently requires more sequential time from start to finish than the deadline permits, even if it were the only task in the entire factory.

- `LOAD c` — where **c** is 1 or 2, indicating that machine **c** is assigned more total work than the duration of the deadline allows it to complete, regardless of how the operations are ordered.

You must output the appropriate certificate for the given inputs. If multiple certificates apply, you may output any valid one.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the processing times of a job on machine 1 and machine 2.

## Output

Print a single line containing the certificate of impossibility: either `JOB i` (where i is the job index) or `LOAD c` (where c is the machine number).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, even if the factory only had to process the first job, it would still fail to meet the 100-unit deadline because of the time it must spend sequentially across the two machines (70 then 60). Thus, `JOB 1` proves the deadline is impossible. In Example 2, no single job violates the deadline on its own, but the first machine is required to operate for a combined 200 time units overall. Since it processes tasks one at a time, it cannot finish within the 150-unit deadline, making `LOAD 1` a valid certificate.

<RATIONALE>
Removed the explicit guarantees that schedule search could be skipped and that exactly one physical constraint would be violated. By framing the task as first evaluating whether any sequence can meet the deadline before outputting a certificate, models must now independently deduce that checking the certificate conditions is mathematically sufficient for the provided test cases, rather than relying on the statement's spoon-fed shortcut.
</RATIONALE>
<PRESERVED_ANSWER>
The test cases inherently trigger the exact same impossibility certificates, and since the output format strictly requires one of these certificates, the correct output string is perfectly preserved.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem remains in the INFEASIBLE class because the core task is still to identify the bottleneck that makes the deadline impossible to meet, which can be done in O(N) time by checking the sequential and aggregate loads.
</PRESERVED_CLASS>
<RISK>
A model could judge the problem ambiguous if it wonders what to output when a schedule is impossible but neither certificate applies, since the explicit promise that one always applies was removed; however, the strict output format implies the test cases are constrained to those where a certificate exists.
</RISK>
