<STATEMENT>
# Problem C — Impossible Deadline: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A manufacturing facility processes **j** orders using two specialized workstations. Each order must first be processed at workstation 1 and subsequently at workstation 2. Each workstation can handle only one order at a time, and an order cannot begin at workstation 2 until its processing at workstation 1 is complete. For each order, you are given its required processing time at workstation 1 ($p1$) and workstation 2 ($p2$).

All orders must be fully completed by a strict deadline **T**. 

For all test cases provided in this problem, it is guaranteed that meeting the deadline **T** is impossible regardless of the processing sequence. Your job is not to search for a schedule; it is to prove impossibility with a short certificate checkable from the input. 

A valid certificate of impossibility demonstrates one of the following bottlenecks:
- A single order **i** (1-based index) cannot be completed in time even if it were the only order, because its sequential processing across workstation 1 then workstation 2 requires a continuous time duration (the sum of its processing times on both workstations) that strictly exceeds the deadline **T**. If this is the case, the certificate is `JOB i`.
- A single workstation **c** (where **c** is 1 or 2) cannot complete its required workload within the deadline, because its cumulative busy interval (the sum of processing times of all orders on workstation **c**) strictly exceeds **T**. If this is the case, the certificate is `LOAD c`.

At least one valid certificate is guaranteed to exist for every test case. If multiple valid certificates exist, you may print any one of them.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the processing times of an order on workstation 1 and workstation 2.

## Output

Print a single line containing a valid certificate of impossibility: either `JOB i` (where i is the order index) or `LOAD c` (where c is the workstation number). If several certificates are valid, print any one of them.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, even if the facility only had to process the first order, it would still fail to meet the 100-unit deadline because of the time it must spend sequentially across the two workstations (70 then 60, total 130). Thus, `JOB 1` proves the deadline is impossible. In Example 2, no single order violates the deadline on its own, but the first workstation is required to operate for a combined 200 time units overall. Since it processes tasks one at a time, it cannot finish within the 150-unit deadline, making `LOAD 1` a valid certificate.
</STATEMENT>
<RATIONALE>
Removed the explicit mathematical inequalities and the guarantee that "Exactly one of the following reasons always applies," replacing them with operational descriptions of the bottleneck and a guarantee that "at least one valid certificate exists." This forces models to translate the operational constraints into the correct summation checks and prevents them from blindly using an `else` fallback without evaluating the final condition.
</RATIONALE>
<PRESERVED_ANSWER>
The conditions for a valid certificate are mathematically identical to the seed's conditions, and allowing any valid certificate ensures that all previously valid outputs remain correct.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem still requires an O(N) pass to check individual job sums and accumulate workstation totals, keeping it in the same complexity class.
</PRESERVED_CLASS>
<RISK>
Models might misinterpret "cumulative busy interval" if they ignore the parenthetical clarification, but the parenthetical makes the arithmetic requirement completely unambiguous.
</RISK>
