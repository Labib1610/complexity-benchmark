<STATEMENT>
# Problem C — Impossible Time Limit: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A system executes **j** tasks through exactly two stages. Every task is executed in stage 1 first and then in stage 2. For each task you are given its duration in stage 1 and in stage 2. Each stage handles only one task at a time, and a task reaches stage 2 only after finishing in stage 1.

Every task must be completely finished by time **T**.

For every input in this problem, it is guaranteed that the time limit cannot be met, no matter how the tasks are ordered. Your goal is not to search for an arrangement; it is to prove the time limit is impossible with a short certificate that can be checked directly against the input.

A valid certificate of impossibility must be provided. By the problem's guarantee, exactly one of the following reasons for impossibility will apply to the input:

- **Sequential Bottleneck**: A single task **i** (1-indexed) cannot be completed within the time limit even if it were the only task in the system. This certificate is valid if and only if the sum of the task's stage 1 and stage 2 durations strictly exceeds **T**. Format this certificate as `JOB i`.
- **Capacity Bottleneck**: A specific stage **c** (**c** is 1 or 2) is assigned more work than can be completed by the deadline. This certificate is valid if and only if the sum of all task durations for stage **c** strictly exceeds **T**. Format this certificate as `LOAD c`.

Output the valid certificate for the given input.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the durations of a task in stage 1 and stage 2.

## Output

Print a single line containing the valid certificate: either `JOB i` (where task **i**'s total duration **p1** + **p2** > **T**) or `LOAD c` (where the total duration on stage **c** exceeds **T**).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, task 1 requires 70 + 60 = 130 time units in sequence. Since 130 > 100, it cannot be completed by time **T**, so `JOB 1` is the valid certificate.
In Example 2, no single task exceeds 150 time units. However, stage 1 must process 50 + 50 + 50 + 50 = 200 time units of work. Since 200 > 150, `LOAD 1` is the valid certificate.
</STATEMENT>
<RATIONALE>
Removed the explicit imperative "If... Print..." step-by-step instructions that allowed models to directly copy the logic flow. Instead, the conditions are presented as formal definitions of validity ("valid if and only if..."). This forces the model to synthesize the checking logic from the definitions rather than matching the procedural pseudo-code pattern provided in the seed text.
</RATIONALE>
<PRESERVED_ANSWER>
The exact same numeric conditions (p1+p2 > T or sum(pc) > T) trigger the exact same outputs (`JOB i` or `LOAD c`), meaning the valid answers are identical for all inputs.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The complexity class remains strictly linear time ($O(j)$) as the solution still only requires checking local sums and aggregate sums against $T$.
</PRESERVED_CLASS>
<RISK>
Models might assume they need to print all valid certificates if multiple exist, but the instruction to "Print a single line containing the valid certificate" and the problem's guarantee that exactly one reason applies mitigates this.
</RISK>
