<STATEMENT>
# Problem C — Impossible Window: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

You are auditing $j$ data-transfer routines. Each routine consists of transmitting a header via Channel 1, followed by transmitting its payload via Channel 2. A channel can only handle one transmission at a time, and a routine's payload transmission cannot begin until its header transmission has completely finished.

There is a strict operational window of $T$ microseconds. All routines must fully complete both of their transmissions within this window.

For every input in this problem, it is guaranteed that the time window is too small, regardless of the order in which the routines are executed. Your task is to output a short text code that proves this impossibility.

Exactly one of the following two bottleneck types will apply. Print the corresponding code:

- `JOB i` (where $i$ is the 1-based index of a violating routine): The window is too short to accommodate the end-to-end routing trace of this specific routine, even under a relaxed schedule where it is granted exclusive, uncontested access to the network.
- `LOAD c` (where $c$ is 1 or 2): The window is too short to accommodate the continuous execution trace of Channel $c$, even under a relaxed schedule where the sequential dependency between headers and payloads is entirely suspended.

## Input

The first line contains two integers $j$ and $T$ ($1 \le j \le 200000$, $1 \le T \le 1000000000$).
Each of the next $j$ lines contains two integers $p_1$ and $p_2$ ($1 \le p_1, p_2 \le 1000000$): the duration in microseconds for the routine's header on Channel 1 and its payload on Channel 2, respectively.

## Output

Print a single line containing either `JOB i` (if routine $i$'s routing trace alone violates the window) or `LOAD c` (if Channel $c$'s continuous execution trace alone violates the window).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, the first routine requires 70 microseconds on Channel 1 and then 60 microseconds on Channel 2 sequentially. It cannot complete its own end-to-end routing trace within the 100-microsecond window, making `JOB 1` a valid proof of impossibility. 

In Example 2, no individual routine's routing trace violates the 150-microsecond window. However, Channel 1 is assigned four header transmissions of 50 microseconds each. Since a channel operates on only one transmission at a time, it cannot complete its continuous execution trace within the window, making `LOAD 1` the valid proof.
</STATEMENT>
<RATIONALE>
I removed the explicit phrases "sequence of operations" and "total active time", which cleanly gave away the `p1 + p2` and `sum(p)` arithmetic shortcuts. Instead, the certificates are defined in terms of scheduling relaxations ("exclusive, uncontested access" and "sequential dependency entirely suspended"). This forces the model to reason about what those relaxed schedules mean for the timeline before deriving the simple additive bounds.
</RATIONALE>
<PRESERVED_ANSWER>
The definitions of the two bottleneck types map perfectly to the original single-job duration and total-channel load checks, ensuring any output valid for the seed remains exactly valid here.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem requires exactly the same $O(N)$ certification logic (checking independent sums and sequential pairs against $T$) as the seed, keeping it in the same complexity class.
</PRESERVED_CLASS>
<RISK>
Models might misinterpret "continuous execution trace" as requiring them to simulate an actual interleaving of jobs, though the clause "where the sequential dependency... is entirely suspended" strictly defines it as a simple sum.
</RISK>
