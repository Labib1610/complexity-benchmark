# Problem C — Pipeline Admission Controller

Time limit: 2 s   Memory limit: 256 MB

## Description

You are implementing Phase 2 of a distributed task management system. The full pipeline consists of:
1. **Ingestion**: Receiving user requests and parsing them.
2. **Admission Control (Your Task)**: Quickly rejecting batches that are mathematically impossible to complete within the user's requested time window.
3. **Scheduling**: Finding the optimal execution order for accepted batches.
4. **Dispatch**: Sending the ordered instructions to the hardware.

You are responsible only for Phase 2. The pipeline routes a batch of **j** jobs to your module along with a maximum time window **T**. Each job requires a certain amount of time on Processor 1, and subsequently a certain amount of time on Processor 2. A job cannot begin on Processor 2 until it has completely finished on Processor 1. Processor 1 and Processor 2 each handle only one job at a time.

Every batch routed to your module in this environment has already been flagged as impossible to complete within **T**. Your program must not search for a schedule; its sole function is to generate a short rejection certificate that the Ingestion module can return to the user. 

A rejection certificate isolates a single component of the system—either one specific job or one specific processor—whose own independent processing requirements strictly exceed the time window **T**, proving the timeline is impossible regardless of scheduling. 

For the provided inputs, exactly one of the following two types of certificates will apply. Print the certificate that holds:

- `JOB i` : Job **i** (1-based index) cannot complete within the window even if it were the only job in the batch.
- `LOAD c` : Processor **c** (1 or 2) cannot complete its assigned tasks within the window even if all its tasks were available immediately and it operated continuously with zero idle time.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200,000, 1 ≤ T ≤ 1,000,000,000).
The next **j** lines each contain two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1,000,000): the required time for the job on Processor 1 and Processor 2, respectively.

## Output

Print a single line containing the certificate: either `JOB i` (where job **i** cannot complete in isolation) or `LOAD c` (where processor **c** cannot complete its tasks in continuous operation).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, even if job 1 were the only job in the system, its sequential processing requirements exceed the 100-unit window. Thus, `JOB 1` is the correct certificate. 
In Example 2, every individual job could finish within the window on its own, but Processor 1 cannot complete its assigned tasks within the 150-unit window even if it ran continuously with zero idle time. Thus, `LOAD 1` is the correct certificate.
</STATEMENT>
<RATIONALE>
Removed the explicit mathematical inequalities (`p1 + p2 > T` and `sum > T`) from the certificate definitions and the example notes. The problem now defines the certificates purely in terms of physical system constraints (a single job running in isolation, or a single processor running continuously without idle time), forcing the model to deduce the underlying sums itself rather than pattern-matching the provided formulas.
</RATIONALE>
<PRESERVED_ANSWER>
The conditions for a job failing in isolation (`p1 + p2 > T`) and a processor failing in continuous operation (`sum(p_c) > T`) are mathematically identical to the original predicates, preserving all outputs.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem still asks for a co-NP style impossibility certificate for a scheduling deadline, keeping it firmly in the INFEASIBLE class.
</PRESERVED_CLASS>
<RISK>
Models might misinterpret "cannot complete in isolation" as only requiring the time on one processor rather than both sequentially, though the description explicitly states a job must finish on Processor 1 before beginning on Processor 2, making the sum the only logical interpretation.
</RISK>
