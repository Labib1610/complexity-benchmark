<STATEMENT>
# SLA Rejection Certificate

Time limit: 2 s   Memory limit: 256 MB

## Description

A two-stage cloud processing pipeline is evaluating a batch of **j** submitted tasks. Each task must undergo sequential processing: it must first be executed on server 1, and only after completion can it be transferred to server 2. Neither server can handle more than one task simultaneously, and a task can only arrive at server 2 after it has completely finished on server 1.

A client has stipulated a Service Level Agreement (SLA) mandating that the entire batch of **j** tasks be fully completed within a strict time limit of **T** milliseconds.

In all provided test cases, this SLA is mathematically impossible to satisfy under any scheduling arrangement. You must produce a concise rejection certificate demonstrating this impossibility, which can be verified directly against the input properties.

An input may have witnesses of both types. If at least one individual-job witness exists and at least one machine-load witness exists, output `LOAD c` for the applicable machine; otherwise output the applicable `JOB i` or `LOAD c` certificate.

The two types of witnesses are:
- **Individual-Job Witness:** The continuous execution time for a specific task (its duration on server 1 plus its duration on server 2) is strictly greater than the SLA limit **T**. The certificate for this is `JOB i`, where **i** is the 1-based index of any such task.
- **Machine-Load Witness:** The sum of all active processing times assigned to a single server across the entire batch is strictly greater than the SLA limit **T**. The certificate for this is `LOAD c`, where **c** is the server number (1 or 2) experiencing the excessive workload.

## Input

The first line provides two integers, **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
The subsequent **j** lines each contain two integers, **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000), indicating the required milliseconds for the task on server 1 and server 2, respectively.

## Output

Output a single line containing the appropriate rejection certificate (`JOB i` or `LOAD c`).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, the first task requires 70 milliseconds on server 1 and 60 milliseconds on server 2. Its uninterrupted duration is 130 milliseconds, which is strictly greater than the 100-millisecond SLA. Therefore, `JOB 1` is a valid individual-job witness.

In Example 2, no single task exceeds the 150-millisecond SLA. However, server 1 has a cumulative active time of 50 + 50 + 50 + 50 = 200 milliseconds, which exceeds the 150-millisecond SLA. Therefore, `LOAD 1` is a valid machine-load witness.
</STATEMENT>
<RATIONALE>
Removed the promise that an input contains exactly one type of bottleneck, replacing it with a tie-breaking rule that prioritizes machine-load witnesses if both are present. This forces models to fully compute machine workloads rather than taking an early-exit shortcut upon finding a single-job witness.
</RATIONALE>
<PRESERVED_ANSWER>
The underlying test cases were originally constructed to have exactly one bottleneck type, so the new tie-breaking condition is never triggered and the required output for every input remains exactly the same.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem still requires checking individual job sums and total machine load sums, maintaining the O(N) verification task in the same complexity class.
</PRESERVED_CLASS>
<RISK>
Models might be slightly confused by the output prefix `JOB i` when the text now refers to them as "tasks", though the output format is explicitly defined.
</RISK>
