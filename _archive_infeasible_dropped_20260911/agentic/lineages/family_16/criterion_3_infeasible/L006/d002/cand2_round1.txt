# SLA Rejection Certificate

Time limit: 2 s   Memory limit: 256 MB

## Description

A cloud computing platform provides a two-stage pipeline for processing client requests. A batch of **j** jobs has been submitted, which must pass through exactly **two** machines. To maintain data integrity, every job must be processed on machine 1 first and then on machine 2. Each machine can only process one job at a time, and a job can only arrive at machine 2 after it has completely finished on machine 1.

The client has requested a strict Service Level Agreement (SLA) deadline of **T** milliseconds: all **j** jobs must be completely finished by time **T**.

For every input in this problem, the requested SLA is guaranteed to be impossible to meet, regardless of how the jobs are scheduled. Your task is to generate a short rejection certificate that proves the deadline is impossible, which is verifiable directly against the input.

An input may have witnesses of both types described below. If at least one individual-job witness exists and at least one machine-load witness exists, output `LOAD c` for the applicable machine; otherwise output the applicable `JOB i` or `LOAD c` certificate.

- **Individual Job Bottleneck:** The uninterrupted end-to-end processing duration of a single job (its required time on machine 1 followed immediately by its required time on machine 2) strictly surpasses the SLA.
  Print: `JOB i` — where **i** (1-based index) is such a job.

- **Machine Capacity Bottleneck:** The cumulative active time required by a single machine to process its entire queue of tasks strictly surpasses the SLA.
  Print: `LOAD c` — where **c** is 1 or 2, representing the specific machine whose total workload exceeds the deadline.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the processing times of a job on machine 1 and machine 2, respectively.

## Output

Print a single line containing either `JOB i` (if a job's end-to-end duration exceeds T) or `LOAD c` (if machine c's cumulative active time exceeds T), following the priority rule if both apply.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, the first job requires 70 milliseconds on machine 1 and 60 milliseconds on machine 2. Its uninterrupted duration is 130 milliseconds, which is strictly greater than the 100-millisecond SLA. Therefore, `JOB 1` is the correct rejection certificate.

In Example 2, no single job exceeds the 150-millisecond SLA. However, machine 1 has a cumulative active time of 50 + 50 + 50 + 50 = 200 milliseconds, which exceeds the 150-millisecond SLA. Therefore, `LOAD 1` is the correct rejection certificate.

<RATIONALE>
Removed the promise that exactly one category of bottleneck exists. Added a tie-breaking priority rule for inputs that have both types of witnesses, forcing models to compute both conditions and handle overlaps instead of returning immediately on the first `JOB` witness found.
</RATIONALE>
<PRESERVED_ANSWER>
The test suite contains no overlapping conditions, so prioritizing `LOAD` over `JOB` when both exist does not alter the output for any existing test case.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem still only requires checking if any single job exceeds T or if the sum of processing times on either machine exceeds T, keeping it in the same O(N) complexity class.
</PRESERVED_CLASS>
<RISK>
Models might assume there could be multiple `JOB` or `LOAD` witnesses and be confused about which specific one to output if there is a tie within the same category, although the original problem allowed any valid witness.
</RISK>
