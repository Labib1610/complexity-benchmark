# SLA Rejection Certificate

Time limit: 2 s   Memory limit: 256 MB

## Description

A cloud computing platform provides a two-stage pipeline for processing client requests. A batch of **j** jobs has been submitted, which must pass through exactly **two** machines. To maintain data integrity, every job must be processed on machine 1 first and then on machine 2. Each machine can only process one job at a time, and a job can only arrive at machine 2 after it has completely finished on machine 1.

The client has requested a strict Service Level Agreement (SLA) deadline of **T** milliseconds: all **j** jobs must be completely finished by time **T**.

For every input in this problem, the requested SLA is guaranteed to be impossible to meet, regardless of how the jobs are scheduled. Your task is to generate a short rejection certificate that proves the deadline is impossible, which is verifiable directly against the input.

There are two categories of witnesses that can prove the SLA failure:

- **Individual Job Witness:** The uninterrupted end-to-end processing duration of a single job (its required time on machine 1 followed immediately by its required time on machine 2) strictly surpasses the SLA.
  Certificate format: `JOB i` — where **i** (1-based index) is any such job. If several jobs satisfy this condition, outputting `JOB i` for any one such index is accepted.

- **Machine Capacity Witness:** The cumulative active time required by a single machine to process its entire queue of tasks strictly surpasses the SLA.
  Certificate format: `LOAD c` — where **c** is 1 or 2, representing any machine whose total workload exceeds the deadline. If both machines satisfy this condition, outputting `LOAD 1` or `LOAD 2` for either overloaded machine is accepted.

An input may have witnesses of both types. If at least one individual-job witness exists and at least one machine-capacity witness exists, you must output `LOAD c` for a qualifying machine; otherwise, output the applicable `JOB i` or `LOAD c` certificate.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the processing times of a job on machine 1 and machine 2, respectively.

## Output

Print a single line containing either `JOB i` (if a job's end-to-end duration exceeds T) or `LOAD c` (if machine c's cumulative active time exceeds T). Follow the priority rule if both witness types exist. Any valid certificate under the applicable category is accepted.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, the first job requires 70 milliseconds on machine 1 and 60 milliseconds on machine 2. Its uninterrupted duration is 130 milliseconds, which is strictly greater than the 100-millisecond SLA. No machine-capacity witness exists. Therefore, `JOB 1` is the correct rejection certificate.

In Example 2, no single job exceeds the 150-millisecond SLA. However, machine 1 has a cumulative active time of 50 + 50 + 50 + 50 = 200 milliseconds, which exceeds the 150-millisecond SLA. Therefore, `LOAD 1` is the correct rejection certificate.
</STATEMENT>
<RATIONALE>
Replaced the explicit promise that test cases contain only one category of bottleneck with a dummy priority rule stating that `LOAD` must be prioritized if both `JOB` and `LOAD` witnesses exist. This forces models to always evaluate both conditions rather than returning immediately upon finding the first `JOB` witness, disabling the early-exit shortcut.
</RATIONALE>
<PRESERVED_ANSWER>
Because the actual test cases were constructed such that the two witness categories are mutually exclusive, the new inter-category priority rule will never be triggered, meaning any output that was valid for the seed remains valid.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The complexity remains strictly linear time (O(N)), as it still only requires computing the sum of processing times for each job and the total load for each machine.
</PRESERVED_CLASS>
<RISK>
Models might get confused by the dummy priority rule and attempt to find a complex scheduling algorithm, though the definition of the witnesses remains simple and independent of scheduling.
</RISK>
