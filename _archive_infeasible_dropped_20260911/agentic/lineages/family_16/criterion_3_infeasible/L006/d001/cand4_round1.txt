# Calibration Denial Sequence

Time limit: 2 s   Memory limit: 256 MB

## Description

A deep-space transit network provides a two-stage calibration sequence for starships. A fleet of **j** vessels has arrived and must pass through exactly **two** calibration stations. To prevent navigational drift, every vessel must be calibrated at Station 1 first, and then at Station 2. Each station is a single-vessel facility that can only process one ship at a time, and a vessel can only enter Station 2 after it has been completely processed by Station 1.

The fleet commander has mandated a strict departure window of **T** chronos: all **j** vessels must be completely finished by time **T**.

For every dataset provided, the requested window is physically impossible to meet, regardless of how the vessels are sequenced. Your task is to generate a short automated denial code that proves the deadline is impossible, which is verifiable directly against the fleet data.

Exactly one of the following failure conditions will always apply. Print the one that holds:

- **Jump Override Breach.** A single vessel is too degraded. Even if a vessel is the only one in the network, its sequential dependency means it cannot finish before the window closes. If a specific vessel **i** (1-based index) requires a total back-to-back duration across both stations that strictly exceeds the window **T**, output the Jump Override Breach code: `JOB i`.

- **Limit Of Active Duration.** A station is over-allocated. A station processes vessels strictly one at a time, so its active time cannot be compressed. If the sheer volume of vessels means Station 1 (or Station 2) requires an aggregate active time across all vessels strictly greater than **T**, output the Limit Of Active Duration code: `LOAD c` (where **c** is 1 or 2, representing the over-allocated station).

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **A** and **E** (1 ≤ A, E ≤ 1000000): the chronos required for the vessel at Station 1 and Station 2, respectively.

## Output

Print a single line containing the exact denial code: either `JOB i` or `LOAD c`.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, vessel 1 requires 70 chronos at Station 1 and 60 chronos at Station 2. Executed back-to-back, this single vessel requires 130 chronos, which is strictly longer than the 100 chronos window. Thus, `JOB 1` is the denial code. 

In Example 2, no single vessel requires more than 150 chronos. However, Station 1 must process four vessels, each taking 50 chronos. The aggregate active time for Station 1 is 200 chronos, which is strictly greater than the 150 chronos window. Thus, `LOAD 1` is the denial code.
</STATEMENT>
<RATIONALE>
The explicit arithmetic instructions ("add up to more than T", "sum of all its processing times") have been replaced with narrative descriptions ("total back-to-back duration", "aggregate active time"). This forces the model to genuinely comprehend the physical constraints of the scenario rather than just parsing the math formulas from the text. Furthermore, the required output strings `JOB` and `LOAD` have been cleverly recontextualized as sci-fi acronyms, stripping away their usual job-shop-scheduling connotations.
</RATIONALE>
