<STATEMENT>
# SLA Rejection Certificate

Time limit: 2 s   Memory limit: 256 MB

## Description

A cloud computing platform provides a two-stage pipeline for processing client requests. A batch of **j** jobs has been submitted, which must pass through exactly **two** machines. To maintain data integrity, every job must be processed on machine 1 first and then on machine 2. Each machine can only process one job at a time, and a job can only arrive at machine 2 after it has completely finished on machine 1.

The client has requested a strict Service Level Agreement (SLA) deadline of **T** milliseconds: all **j** jobs must be completely finished by time **T**.

For every input in this problem, the requested SLA is guaranteed to be impossible to meet, regardless of how the jobs are scheduled. Your task is to generate a short rejection certificate that proves the deadline is impossible, which is verifiable directly against the input.

Multiple rejection reasons may apply simultaneously. You must evaluate the following conditions and print the certificate for the first one that applies, strictly following this priority order:

1. **Machine 1 is overloaded.** Because a machine processes jobs one at a time, it requires a time span at least equal to the sum of all its processing times. If the total processing time required on machine 1 exceeds **T**, the deadline is impossible.
   Print: `LOAD 1`

2. **Machine 2 is overloaded.** Similarly, if the total processing time required on machine 2 exceeds **T**, the deadline is impossible.
   Print: `LOAD 2`

3. **A single job is too long.** If a specific job's processing times on both machines add up to more than **T**, that job alone (running on machine 1 then machine 2, in sequence) cannot finish by **T**. This certificate is only accepted when neither machine load exceeds **T**.
   Print: `JOB i` — where **i** (1-based index) is the first such job.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the processing times of a job on machine 1 and machine 2, respectively.

## Output

Print a single line: `LOAD 1`, `LOAD 2`, or `JOB i` (where **i** is the 1-based index of the first job whose p1 + p2 exceeds T), strictly adhering to the priority order specified in the description.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, neither machine's total load exceeds 100 (machine 1 sum is 75, machine 2 sum is 66). However, job 1 needs 70 + 60 = 130 > 100 milliseconds in sequence. Since no machine is overloaded, `JOB 1` is the correct rejection certificate. In Example 2, machine 1 must process 50+50+50+50 = 200 > 150 milliseconds of work in total, so `LOAD 1` is the rejection certificate.
</STATEMENT>
<RATIONALE>
I removed the guarantee that exactly one rejection reason applies and replaced it with a strict overlapping-case priority rule that requires checking machine loads before individual jobs. This forces models to compute the total load for both machines rather than relying on early-exit shortcuts that trigger as soon as a single long job is found.
</RATIONALE>
<PRESERVED_ANSWER>
Because the original test cases guaranteed that exactly one rejection reason applied per input, introducing a priority order for theoretical overlaps does not alter the correct output for any existing test case.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem remains in the same O(N) verification class, as finding the correct certificate still only requires a single linear pass to compute machine sums and check individual job lengths.
</PRESERVED_CLASS>
<RISK>
Models might assume the priority order implies they must store all jobs in memory to check them after computing loads, but the memory limit easily accommodates storing the 200,000 integer pairs.
</RISK>
