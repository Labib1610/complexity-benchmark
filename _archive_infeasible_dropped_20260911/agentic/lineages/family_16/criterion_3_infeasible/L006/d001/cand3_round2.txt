# Cloud Pipeline SLA Validator

Time limit: 2 s   Memory limit: 256 MB

## Description

A distributed computing environment features a pipeline with exactly two specific servers for handling data processing batches. A submitted batch consists of **j** indivisible tasks. To ensure correct execution, each task must first be executed on server 1, and only after its completion there, can it be transferred to server 2. Both servers are strictly sequential, meaning each can execute only a single task at any given moment.

Clients submit their batches alongside a hard Service Level Agreement (SLA) threshold of **T** milliseconds. The SLA dictates that the entirety of the **j** tasks must be fully completed on both servers within **T** milliseconds from the start.

In this scenario, every provided dataset represents a batch where fulfilling the SLA is fundamentally impossible, no matter what scheduling strategy is employed. Your objective is to output a concise proof (a rejection certificate) demonstrating this impossibility, which can be verified directly against the given data.

It is guaranteed that at least one of the following rejection conditions is met. Output any one valid certificate that correctly proves the SLA is impossible:

- **Individual Task Violation:** If the combined duration of a single task across both servers exceeds **T**, it is physically impossible for that task to complete within the SLA (since it must run sequentially on server 1 then server 2).
  Output format: `JOB i` (where **i** is the 1-based index of any such task).

- **Server Capacity Exceeded:** Since a server processes tasks sequentially, the absolute minimum time it needs is the sum of all task durations assigned to it. If the aggregate processing time required by all tasks on server 1, or alternatively on server 2, is strictly greater than **T**, the SLA cannot be met.
  Output format: `LOAD c` (where **c** is either 1 or 2, indicating a server that is overallocated).

## Input

The first line provides two integers, **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000), representing the number of tasks and the SLA deadline in milliseconds.
Following this are **j** lines, each containing two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000). These represent the milliseconds required to process that particular task on server 1 and server 2, respectively.

## Output

Output exactly one line containing a valid proof of impossibility matching one of the formats: `JOB i` (if task **i**'s total time p1 + p2 > T) or `LOAD c` (if the sum of all processing times on server **c** > T).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, the first task requires 70 + 60 = 130 milliseconds of sequential execution. Since 130 > 100, `JOB 1` is a valid proof of impossibility.
In Example 2, no individual task exceeds the 150-millisecond limit. However, server 1 is required to do 50 + 50 + 50 + 50 = 200 milliseconds of work. Since 200 > 150, `LOAD 1` is a valid proof.

<RATIONALE>
The explicit guarantee that "Exactly one of the following rejection reasons always applies" was removed. Instead, the problem now states that "at least one" condition is met and allows outputting "any one valid certificate". This change prevents models from relying on the text to assume mutual exclusivity, forcing them to reason about the validity of their condition checks without a guaranteed single correct path, while strictly preserving the allowed output set and avoiding the G3-violating priority rules from the previous attempt.
</RATIONALE>

The conditions for a valid certificate (`JOB i` or `LOAD c`) are identical to the seed, and any valid certificate is accepted, meaning the reference solution's correct output remains perfectly valid.
