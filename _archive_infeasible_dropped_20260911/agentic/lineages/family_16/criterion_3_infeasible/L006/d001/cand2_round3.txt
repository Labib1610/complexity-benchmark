# SLA Rejection Certificate

Time limit: 2 s   Memory limit: 256 MB

## Description

A cloud computing platform provides a two-stage pipeline for processing client requests. A batch of **j** jobs has been submitted, which must pass through exactly **two** machines. To maintain data integrity, every job must be processed on machine 1 first and then on machine 2. Each machine can only process one job at a time, and a job can only arrive at machine 2 after it has completely finished on machine 1.

The client has requested a strict Service Level Agreement (SLA) deadline of **T** milliseconds: all **j** jobs must be completely finished by time **T**.

For every input in this problem, the requested SLA is guaranteed to be impossible to meet, regardless of how the jobs are scheduled. Your task is to generate a short rejection certificate that proves the deadline is impossible, which is verifiable directly against the input.

To standardize the rejection certificates across cases where multiple bottlenecks might exist, you must evaluate the following failure conditions in this exact priority order and print the certificate for the first condition that applies (it is guaranteed that at least one condition will be met):

1. **Machine 1 Overload**: Because machine 1 processes jobs one at a time, it requires a time span at least equal to the sum of all its processing times. If the total processing time required on machine 1 exceeds **T**, the deadline is impossible. Print: `LOAD 1`.
2. **Machine 2 Overload**: Similarly, if the total processing time required on machine 2 exceeds **T**, print: `LOAD 2`.
3. **Job Bottleneck**: If a specific job's processing times on both machines add up to more than **T**, that job alone (running on machine 1 then machine 2, in sequence) cannot finish by **T**. Print: `JOB i` — where **i** (1-based index) is such a job. If multiple jobs satisfy this condition, you may print the certificate for any one of them.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the processing times of a job on machine 1 and machine 2, respectively.

## Output

Print a single line containing the standardized rejection certificate. Following the required priority order, output `LOAD 1` if machine 1 is overloaded. If not, output `LOAD 2` if machine 2 is overloaded. If neither machine is overloaded, output `JOB i` for any job **i** whose combined processing time exceeds **T**.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, the total load on machine 1 is 75 (≤ 100) and on machine 2 is 66 (≤ 100), so neither machine is overloaded. Job 1 needs 70 + 60 = 130 > 100 milliseconds in sequence. Since the higher-priority machine overload conditions are not met, the job bottleneck condition applies, so `JOB 1` is the correct rejection certificate.

In Example 2, no single job exceeds 150 milliseconds. However, machine 1 must process 50+50+50+50 = 200 > 150 milliseconds of work in total. This triggers the first priority condition, so `LOAD 1` is the rejection certificate.
</STATEMENT>
<RATIONALE>
Removed the guarantee that exactly one condition applies, replacing it with an explicit priority order for overlapping conditions. This forces models to fully process the machine loads before emitting a job certificate, breaking the shortcut of returning early on the first oversized job.
</RATIONALE>
<PRESERVED_ANSWER>
Because the original test cases guarantee that exactly one condition applies, the new priority rules will never override a valid certificate, ensuring identical output.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem still requires only O(N) time and O(1) space to compute sums and find the maximum sequential job time, keeping it in the same complexity class.
</PRESERVED_CLASS>
<RISK>
Models might assume they must print the smallest index `i` if multiple jobs bottleneck, though the prompt explicitly states any valid `i` is acceptable.
</RISK>
