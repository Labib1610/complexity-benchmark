# Impossible Deadline: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A technology company is deploying a system update consisting of **j** distinct modules. The deployment process requires two sequential phases: first, each module must be compiled on a singular build server (Phase 1), and subsequently verified on a singular testing server (Phase 2). Each server can process only one module at any given moment. A module can only begin its verification phase after its compilation phase has entirely concluded.

The company has mandated a fixed deployment timeframe of exactly **T** minutes. Every module must finish its verification before this timeframe expires at minute **T**.

The given configurations represent unachievable deployment schedules—no valid processing order exists that can finish all modules within the given timeframe. Your objective is not to find a schedule, but to output a short certificate that demonstrates why the timeframe is impossible to meet.

One or more of the following impossibility certificates will apply to the configuration. If multiple certificates are valid, you must apply the following tie-breaking rules:
1. Any valid `JOB` certificate takes strict precedence over any `LOAD` certificate.
2. If multiple `JOB` certificates are valid, output the `JOB i` certificate with the highest module index **i**.
3. If no `JOB` certificate is valid but both `LOAD 1` and `LOAD 2` are valid, output `LOAD 2`.

- **Module Delay.** Any valid schedule must allocate two sequential time intervals for a module's compilation and verification within the deployment timeframe. If it is mathematically impossible to accommodate these two sequential intervals for a given module within the timeframe [0, **T**] such that their durations match the module's requirements, output `JOB i`, where **i** is the 1-based index of the module.
- **Server Saturation.** Any valid schedule must allocate non-overlapping time intervals on a server for all modules within the deployment timeframe. If it is mathematically impossible to pack one non-overlapping interval per module on server **c** within the timeframe [0, **T**] such that the durations match the modules' requirements on that server, output `LOAD c` (where **c** is 1 for the build server and 2 for the testing server).

## Input

The first line provides two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
The subsequent **j** lines each provide two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000), representing the compilation duration and the verification duration of a module, respectively.

## Output

Print a single line containing `JOB i` (for a module delay certificate) or `LOAD c` (for a server saturation certificate), following the tie-breaking rules if multiple certificates are valid.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, for module 1, its compilation and verification take 70 and 60 minutes respectively. It is impossible to fit two sequential intervals of lengths 70 and 60 within the 100-minute window, making `JOB 1` a valid proof of impossibility. Since no other module violates the constraints, `JOB 1` is the correct output. In Example 2, no single module requires sequential intervals exceeding 150 minutes in total, but the build server requires intervals of lengths 50, 50, 50, and 50. It is impossible to place these four non-overlapping intervals inside the 150-minute window. Thus `LOAD 1` is the correct output.

<RATIONALE>
Replaced the guarantee that exactly one bottleneck is present with explicit tie-breaking rules for when multiple bottlenecks occur. This prevents models from using the shortcut of returning the first valid certificate they encounter, forcing them to process the entire list and aggregate the results before making a decision.
</RATIONALE>
<PRESERVED_ANSWER>
Since the original problem guaranteed exactly one bottleneck per valid input, the newly introduced tie-breaking rules will never alter the output for any test case in the original suite, keeping all answers identical.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The complexity class remains INFEASIBLE, as the solution still only requires a single O(N) pass to verify individual module limits and aggregate server loads.
</PRESERVED_CLASS>
<RISK>
Models might assume that the possibility of multiple bottlenecks implies a more complex scheduling check, but the certificates are still evaluated using the same mathematical conditions.
