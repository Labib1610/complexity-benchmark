# Problem C — Impossible Deadline: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A software firm is rolling out an update comprising **j** independent modules. The rollout involves two stages: a build phase on a dedicated compilation server (Stage 1), followed by a testing phase on a dedicated validation server (Stage 2). Each server handles exactly one module at a time. A module is eligible for the testing server only after its build phase has completely finished.

The firm has allocated a strict release window of exactly **T** minutes. All modules must be fully tested before this window closes at minute **T**.

Every provided scenario represents an impossible timeline—there is no valid scheduling order that can complete all modules within the release window. Instead of attempting to schedule, your task is to identify a structural limit that proves the timeline is unachievable, providing a short certificate the system can verify.

In every provided scenario, one or more of the following fundamental limits is breached. Output a certificate for any one breached limit. (If multiple limits are breached, or multiple modules/servers breach a limit, output **any** one valid certificate.)

- **Sequential Dependency Conflict.** For any given module, the testing phase cannot commence until its build phase has fully concluded. If a module's inherent sequential processing footprint—the continuous time span from the start of its build phase to the completion of its testing phase, assuming zero wait time between stages—strictly exceeds the **T** allowable minutes, output `JOB i`, where **i** is the module's 1-based index. If several modules satisfy this conflict, print **any one** of their indices.
- **Hardware Saturation.** Each dedicated server can only process one module at a time. Consequently, the total footprint of active processing time required on a server is the accumulation of its phase durations for all **j** modules. If this cumulative footprint for a specific server is strictly greater than the **T** allowable minutes, output `LOAD c`, where **c** is 1 for the compilation server or 2 for the validation server. If both servers are saturated, print **either** `LOAD 1` or `LOAD 2`.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the build duration and testing duration of a module.

## Output

Print one line: `JOB i` (for a sequential dependency conflict) or `LOAD c` (for hardware saturation), where the printed witness satisfies the stated condition.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, for module 1, its build and testing phases take 70 and 60 minutes respectively. Its inherent sequential processing footprint is 130 minutes. Since this strictly exceeds the 100-minute window, `JOB 1` is a correct proof of impossibility. In Example 2, no single module requires a sequential footprint exceeding 150 minutes, but the compilation server requires a cumulative footprint of 200 active minutes. It is mathematically impossible to fit this within the 150-minute window without overlapping. Thus `LOAD 1` is a correct output.

<RATIONALE>
The previous wording guaranteed that "exactly one" bottleneck would be present, which allowed models to confidently use elimination (e.g., `if not JOB and not LOAD 1: return LOAD 2`). I removed this affordance by explicitly stating that "one or more" limits may be breached and explicitly permitting any valid certificate if multiple exist. This forces models to defensively evaluate all conditions rather than relying on assumed mutual exclusivity, while adhering strictly to the expert critique to avoid introducing a novel tie-breaking rule that would violate the original output contract.
