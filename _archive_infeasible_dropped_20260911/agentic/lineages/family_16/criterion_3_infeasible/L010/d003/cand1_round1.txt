# Problem C — Impossible Deadline: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A software firm is deploying an update with **j** independent modules. The deployment has two phases: compilation on a build server (Phase 1), and then validation on a testing server (Phase 2). Each server processes at most one module at a time. A module can only start validation after its compilation is fully complete.

The firm has set a strict deployment window of exactly **T** minutes. Every module must finish both phases before this window expires at minute **T**.

In every given scenario, the timeline is impossible—no valid schedule can finish all modules within the deployment window. Your task is to identify a bottleneck that proves the timeline cannot be met, and provide a short certificate for the system.

One or more of the following bottlenecks might occur. If several certificates are valid, you must output the `JOB` certificate for the module with the highest index. If no `JOB` certificate applies, output `LOAD 2` if it is a valid certificate, otherwise output `LOAD 1`:

- **Module Delay.** A valid schedule requires a module's compilation and validation to run as two sequential intervals inside the deployment window. If it is mathematically impossible to fit these two sequential intervals for a specific module inside the window [0, **T**] with lengths equal to its required compilation and validation times, output `JOB i`, where **i** is the 1-based index of the module.
- **Server Saturation.** A valid schedule requires a server to run its phase for all modules as non-overlapping intervals within the deployment window. If it is mathematically impossible to place one non-overlapping interval per module on server **c** inside the window [0, **T**] such that each interval's length equals the module's required time for that server, output `LOAD c`, where **c** is 1 for the build server or 2 for the testing server.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the compilation duration and validation duration of a module.

## Output

Print a single line: `JOB i` (for a module bottleneck) or `LOAD c` (for a server bottleneck), following the tie-breaking rules if multiple apply.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, for module 1, its compilation and validation take 70 and 60 minutes respectively. It is impossible to fit two sequential intervals of lengths 70 and 60 within the 100-minute window, making `JOB 1` a valid proof of impossibility. Since no other bottlenecks are present, it is the correct output according to the tie-breaking rules. In Example 2, no single module requires sequential intervals exceeding 150 minutes in total, but the build server requires intervals of lengths 50, 50, 50, and 50. It is impossible to place these four non-overlapping intervals inside the 150-minute window. Thus `LOAD 1` is the correct output.
</STATEMENT>
<RATIONALE>
Removed the promise that exactly one bottleneck is present, which allowed models to short-circuit and return the first JOB certificate they found. Added a tie-breaking rule prioritizing the highest index JOB and reversing the LOAD priority, forcing models to evaluate all jobs rather than returning early on a match.
</RATIONALE>
<PRESERVED_ANSWER>
The hidden test cases only ever contain exactly one valid bottleneck, so the tie-breaking rule will never change the final output, preserving identical answers.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem still requires checking individual job lengths and aggregate machine loads against T, keeping it in the same impossibility certification class.
</PRESERVED_CLASS>
<RISK>
Models might assume there are test cases with multiple bottlenecks and write slightly less efficient code to handle the tie-breaking, but this will not cause them to time out since the linear scan remains O(N).
</RISK>
