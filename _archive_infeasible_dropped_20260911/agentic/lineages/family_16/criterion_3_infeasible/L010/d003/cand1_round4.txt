# Problem C — Impossible Deadline: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A software firm is rolling out an update comprising **j** independent components. The rollout involves two stages: compilation on a dedicated build machine (Stage 1), followed by validation on a dedicated testing machine (Stage 2). A machine handles exactly one component at a time. A component is eligible for the testing machine only when its compilation has completely finished.

The firm has allocated a strict release window of exactly **T** minutes. All components must be fully validated before this window closes at minute **T**.

Every provided scenario represents an impossible timeline—there is no valid scheduling order that can complete all components within the release window. Instead of scheduling, your task is to identify a bottleneck that proves the timeline is unachievable, providing a short certificate the system can verify.

One or more bottlenecks may be present. If multiple certificates are valid, output the `JOB` certificate with the largest component index; if no `JOB` certificate is valid, output `LOAD 2` if valid, otherwise `LOAD 1`.

The certificates are defined as follows:

- **Component Delay.** A valid schedule requires a component's compilation and validation phases to be executed sequentially within the release window. If it is mathematically impossible for a specific component to complete both phases inside the window [0, **T**] because its total required duration exceeds **T**, this is a component bottleneck. The certificate is `JOB i`, where **i** is the 1-based index of the component.
- **Machine Saturation.** A valid schedule requires a machine to execute its phase for all components without overlapping within the release window. If it is mathematically impossible for machine **c** to process all components inside the window [0, **T**] because the sum of durations required on that machine exceeds **T**, this is a machine bottleneck. The certificate is `LOAD c`, where **c** is 1 for the build machine or 2 for the testing machine.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the compilation duration and validation duration of a component.

## Output

Print a single line containing the certificate that fits the tie-breaking rules: either `JOB i` or `LOAD c`.

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, for component 1, its compilation and validation take 70 and 60 minutes respectively. Their sum exceeds the 100-minute window, making `JOB 1` a valid proof of impossibility. Since it is the only component delay bottleneck, it is the correct output. In Example 2, no single component requires sequential intervals exceeding 150 minutes in total, but the build machine requires 50 + 50 + 50 + 50 = 200 minutes. It is impossible to process all components on the build machine within the 150-minute window. Thus `LOAD 1` is the correct output.
</STATEMENT>
<RATIONALE>
Replaced the "exactly one bottleneck" guarantee with a tie-breaking rule for multiple bottlenecks, as specified in the strategy. This removes the affordance of returning the first valid certificate found, forcing models to implement the full scan and tie-breaking logic. Additionally, the interval-packing language was simplified to direct sum conditions to avoid structural giveaways, and the flagged word 'matching' was removed.
</RATIONALE>
