# Problem C — Impossible Allocation: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A central server must synchronize $j$ active databases over a strict window of $T$ seconds. For each database $i$, the server must transmit exactly $p1_i$ Delta chunks and exactly $p2_i$ Snapshot chunks. 

The server features two independent transmission channels: one for Delta chunks and one for Snapshot chunks. This imposes the following global bandwidth limits:
- The Delta channel can transmit at most one Delta chunk per second in total (across all databases).
- The Snapshot channel can transmit at most one Snapshot chunk per second in total (across all databases).

Furthermore, the server enforces a strict data consistency protocol. For a schedule to be valid, it must satisfy a countdown tracker for every database. For each database $i \in \{1, \dots, j\}$, its tracker $U_i$ is initialized to $p2_i$. During each second $k$ from $1$ to $T$ (in chronological order), the server updates $U_i$ via two sequential steps:
1. If second $k$ contains a Snapshot chunk for database $i$, $U_i$ is decreased by $1$.
2. If second $k$ contains a Delta chunk for database $i$, $U_i$ is restored to $p2_i$.

A schedule is valid only if, for all databases $i$, the final value of $U_i$ after second $T$ is exactly $0$.

Every provided configuration is mathematically impossible to complete—there is no valid way to construct the schedule to accommodate all required chunks while satisfying the countdown tracker for all databases. Your task is to identify the bottleneck that proves the configuration is unachievable.

Exactly one of the following foundational requirements is broken. Output the applicable certificate:

- **Phase Violation:** For some database $i$, it is mathematically impossible to schedule its $p1_i$ Delta chunks and $p2_i$ Snapshot chunks within $T$ seconds such that its final tracker $U_i$ equals $0$ (even if it were the only database on the server). Output `JOB i` (where $i$ is the 1-based index of the database).
- **Delta Saturation:** It is impossible to schedule all required Delta chunks for all $j$ databases within $T$ seconds. Output `LOAD 1`.
- **Snapshot Saturation:** It is impossible to schedule all required Snapshot chunks for all $j$ databases within $T$ seconds. Output `LOAD 2`.

You are guaranteed that exactly one of these requirements will be broken for the given input.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the required number of Delta chunks and Snapshot chunks respectively for database $i$ (i.e., $p1_i$ and $p2_i$).

## Output

Print a single line: `JOB i` (for a Phase Violation) or `LOAD c` (for a saturation failure, where **c** is 1 for Delta saturation or 2 for Snapshot saturation).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, database 1 requires 70 Delta chunks and 60 Snapshot chunks. To achieve a final tracker $U_1 = 0$, the 60 Snapshot decrements must not be interrupted by a Delta chunk's restoration to 60. Thus, the 70 Delta chunks and 60 Snapshot chunks require distinct, non-overlapping seconds in a specific order. Since $70 + 60 = 130 > 100$, this is impossible. Thus `JOB 1` is the correct proof of impossibility. 

In Example 2, no single database violates the phase tracker on its own. However, the sum of required Delta chunks across all 4 databases is 200. Since the Delta channel can only send 1 chunk per second, it is impossible to schedule them all in $150$ seconds. Thus `LOAD 1` is the correct output.
