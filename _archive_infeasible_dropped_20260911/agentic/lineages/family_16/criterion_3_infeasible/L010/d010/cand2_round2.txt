<STATEMENT>
# Problem C — Impossible Allocation: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A central server must execute $j$ complex tasks over a strict window of $T$ milliseconds. For each task $i$, the server must schedule exactly $p1_i$ Preparation cycles and exactly $p2_i$ Execution cycles. 

The server has two independent processors. This means:
- Across all tasks, the Preparation processor can execute at most one Preparation cycle per millisecond.
- Across all tasks, the Execution processor can execute at most one Execution cycle per millisecond.

Additionally, the server enforces a strict task integrity protocol. For a schedule to be valid, it must satisfy a tracking mechanism for every task. For each task $i \in \{1, \dots, j\}$, an integrity register $W_i$ (capable of holding arbitrarily large integers) is initialized to $p1_i$. During each millisecond $k$ from $1$ to $T$ (in chronological order), the server updates $W_i$ via two sequential steps:
1. If millisecond $k$ contains an Execution cycle for task $i$, $W_i$ is replaced by $W_i \times (W_i + 1)$.
2. If millisecond $k$ contains a Preparation cycle for task $i$, $W_i$ is decreased by $1$.

A schedule is valid only if, for all tasks $i$, the final value of $W_i$ after millisecond $T$ is exactly $0$.

Every provided configuration is mathematically impossible to complete—there is no valid way to construct the schedule to accommodate all required cycles while satisfying the integrity register for all tasks. Your task is to identify the bottleneck that proves the configuration is unachievable.

Exactly one of the following foundational requirements is broken. Output the applicable certificate:

- **Task Violation:** For some task $i$, it is mathematically impossible to schedule its $p1_i$ Preparation cycles and $p2_i$ Execution cycles within $T$ milliseconds such that its final register $W_i$ equals $0$ (even if it were the only task on the server). Output `JOB i` (where $i$ is the 1-based index of the task).
- **Preparation Saturation:** It is impossible to schedule all required Preparation cycles for all $j$ tasks within $T$ milliseconds. Output `LOAD 1`.
- **Execution Saturation:** It is impossible to schedule all required Execution cycles for all $j$ tasks within $T$ milliseconds. Output `LOAD 2`.

You are guaranteed that exactly one of these requirements will be broken for the given input.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the required number of Preparation cycles and Execution cycles respectively for task $i$ (i.e., $p1_i$ and $p2_i$).

## Output

Print a single line: `JOB i` (for a Task Violation) or `LOAD c` (for a saturation failure, where **c** is 1 for Preparation saturation or 2 for Execution saturation).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, task 1 requires 70 Preparation cycles and 60 Execution cycles. Its register $W_1$ starts at 70. Since there are exactly 70 Preparation cycles scheduled for task 1, the total possible decrease to $W_1$ over the window is exactly 70. To achieve a final register $W_1 = 0$, the register must not experience any net increase from Execution cycles. If an Execution cycle occurs when $W_1 > 0$, the operation $W_1 \times (W_1 + 1)$ strictly increases $W_1$ by at least 2, making it impossible for the remaining Preparation cycles to bring $W_1$ down to 0. Thus, $W_1$ must be exactly 0 whenever an Execution cycle occurs. This implies all 70 Preparation cycles must be scheduled strictly before any of the 60 Execution cycles. Since $70 + 60 = 130 > 100$, this is mathematically impossible. Thus `JOB 1` is the correct proof of impossibility. 

In Example 2, no single task violates its register requirements on its own. However, the sum of required Preparation cycles across all 4 tasks is 200. Since the server can only execute 1 Preparation cycle per millisecond, it is impossible to schedule them all in $150$ milliseconds. Thus `LOAD 1` is the correct output.
</STATEMENT>
<RATIONALE>
The previous tracker (where Delta sets to 0) was easily recognized as a standard "all Deltas before all Snapshots" precedence constraint, leading models to blindly write `p1 + p2 > T`. I replaced this with a non-linear polynomial update rule: $W_i$ starts at $p1_i$, Preparation cycles subtract 1, and Execution cycles multiply $W_i$ by $(W_i + 1)$. Because the total possible subtraction is exactly $p1_i$, any Execution cycle occurring when $W_i > 0$ permanently inflates the register beyond the remaining subtractive capacity. This mathematically enforces the exact same precedence constraint (all Preparation cycles must precede all Execution cycles) but requires genuine algebraic reasoning to discover, defeating surface-level pattern matchers.
</RATIONALE>
<PRESERVED_ANSWER>
The non-linear recurrence strictly requires all $p1_i$ Preparation cycles to finish before any Execution cycles begin to reach the target of 0, preserving the exact $p1_i + p2_i \le T$ feasibility condition for each task, while the global resource limits remain exactly 1 per time unit.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem still requires an $O(N)$ linear scan to check if $p1_i + p2_i > T$ for any task or if $\sum p1_i > T$ or $\sum p2_i > T$, keeping it firmly in the same simple feasibility-checking complexity class.
</PRESERVED_CLASS>
