<STATEMENT>
# Problem C — Impossible Deadline: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A data center must resolve **j** queries. Processing each query requires completing a data retrieval phase on the storage array (Component 1) for exactly **p1** minutes, and an analysis phase on the compute node (Component 2) for exactly **p2** minutes. A query is considered completely finished only when both of its phases have been fully executed.

The system normally operates under strict constraints:
- **Intra-query sequential dependency:** A query can only begin its Component 2 phase after its Component 1 phase is entirely complete.
- **Component 1 concurrency limit:** The storage array can process at most one query at any given moment.
- **Component 2 concurrency limit:** The compute node can process at most one query at any given moment.
- **Deadline:** All phases of all queries must be completely finished by time **T**.

For every input in this problem, it is **guaranteed that the deadline cannot be met**, no matter how the system schedules the queries. Your task is to **prove** the deadline is impossible by identifying a hypothetical relaxation of the system constraints that *still* fails to meet the deadline. 

It is guaranteed that exactly one of the following three relaxed scenarios will inevitably fail to finish all queries by time **T** (while the remaining two scenarios could theoretically meet the deadline in their relaxed states). Output the certificate for the unique scenario that fails:

- **Relaxed Scenario A:** The hardware concurrency limits are completely lifted. Both Component 1 and Component 2 can process an unlimited number of queries simultaneously. However, the intra-query sequential dependency remains strictly enforced: no query may begin its Component 2 phase until its own Component 1 phase is entirely complete. You must determine if the absolute minimum time required to finish all queries exceeds **T**. If it does, print `JOB i`, where **i** is the 1-based index of the specific query that inevitably forces the completion time past **T**.
- **Relaxed Scenario B:** The intra-query sequential dependencies are completely lifted, meaning any query may begin its Component 2 phase at time 0, concurrently with its Component 1 phase. The concurrency limit on Component 2 is also lifted, allowing it to process an unlimited number of queries simultaneously. However, Component 1 retains its original bottleneck: it can process at most one query at any given moment. You must determine the absolute minimum time required to completely finish all phases of all queries under these relaxed rules. If this minimum possible completion time strictly exceeds **T**, print `LOAD 1`.
- **Relaxed Scenario C:** The intra-query sequential dependencies are completely lifted, meaning any query may begin its Component 2 phase at time 0. The concurrency limit on Component 1 is also lifted, allowing it to process an unlimited number of queries simultaneously. However, Component 2 retains its original bottleneck: it can process at most one query at any given moment. You must determine the absolute minimum time required to completely finish all phases of all queries under these relaxed rules. If this minimum possible completion time strictly exceeds **T**, print `LOAD 2`.

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the required minutes of the query on Component 1 and Component 2.

## Output

Print a single line containing the certificate:
- `JOB i` (where **i** is the 1-based query index for which Relaxed Scenario A fails)
- `LOAD c` (where **c** is 1 if Relaxed Scenario B fails, or 2 if Relaxed Scenario C fails)

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, under Relaxed Scenario A, all queries can run simultaneously on both components, but each query must complete Component 1 before starting Component 2. The minimum time to finish query 1 is 70 + 60 = 130 minutes. Queries 2 and 3 require 4 and 7 minutes respectively. The absolute minimum time to finish all queries is max(130, 4, 7) = 130 minutes. Since this strictly exceeds the deadline of 100, and query 1 is the one forcing the time past the deadline, `JOB 1` is the certificate.

In Example 2, under Relaxed Scenario A, the minimum time is 50 + 1 = 51 minutes, which meets the deadline. However, under Relaxed Scenario B, queries can start Component 2 immediately at time 0 and run on Component 2 simultaneously, but Component 1 can only process one query at a time. Component 1 will take 50 + 50 + 50 + 50 = 200 minutes to finish all queries. Component 2 will take max(1, 1, 1, 1) = 1 minute. The absolute minimum time to finish all phases is max(200, 1) = 200 minutes. Since 200 strictly exceeds 150, `LOAD 1` is the certificate.
</STATEMENT>
<RATIONALE>
Replaced the degenerate "0-time" relaxations with concurrent/serial makespan evaluations. This preserves the exact logical failure conditions (due to the problem's guarantee that exactly one scenario fails), but forces models to analyze a non-trivial scheduling setup (e.g. `max(sum(p1), max(p2)) > T`) rather than pattern-matching the explicit additive bounds.
</RATIONALE>
<PRESERVED_ANSWER>
Under the problem's guarantee that exactly one of the original bounds fails, the new makespan bounds evaluate to exactly the same truth values (e.g. max(sum(p1), max(p2)) > T is uniquely true if and only if sum(p1) > T).
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The complexity class remains INFEASIBLE as the solution still requires an O(N) scan to evaluate the three makespan conditions and identify the single failure.
</PRESERVED_CLASS>
<RISK>
Models might misinterpret the minimum time calculation in Scenario B/C if they fail to realize that the serial component defines the dominant completion time, though the Note explicitly works through this exact `max` logic.
</RISK>
