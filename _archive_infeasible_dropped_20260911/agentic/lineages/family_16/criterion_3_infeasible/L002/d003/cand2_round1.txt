# Problem C — Impossible Deadline: Certify It

Time limit: 2 s   Memory limit: 256 MB

## Description

A chef is preparing a banquet featuring **j** special recipes, tracked in the kitchen's order system as `JOB`s. Every `JOB` must be processed in appliance 1 (the oven) and subsequently in appliance 2 (the broiler). For each `JOB` you are given the exact number of minutes it must occupy appliance 1, and the exact number of minutes it must occupy appliance 2. Each appliance can only accommodate one `JOB` at any given moment, and a `JOB` can only transition to appliance 2 after its appliance 1 phase is entirely complete.

The kitchen operates under a strict deadline: all processing for all `JOB`s must be completely finished by time **T**.

For every input in this problem, it is **guaranteed that the deadline cannot be met**, no matter how the chef schedules the processing. Your task is not to search for a schedule; it is to **prove** the deadline is impossible with a short certificate that can be checked directly against the input.

Exactly one of the following reasons is guaranteed to apply for every input. Print the certificate corresponding to the unique applicable reason:

- **A single recipe has negative slack.** If a recipe is granted exclusive access starting exactly at time 0, and we measure the slack between its oven completion time and the latest possible moment it must enter the broiler to finish exactly at the deadline, this slack is strictly negative.
  Print: `JOB i` — where **i** (1-based) is such a recipe.

- **An appliance's cumulative occupancy is excessive.** Because an appliance operates non-concurrently, its theoretical maximum continuous uptime is bounded by the deadline **T**. If we pack every recipe's required time for a specific appliance into a single continuous block, this cumulative occupancy surpasses the maximum available uptime.
  Print: `LOAD c` — where **c** is 1 (if the oven's cumulative occupancy surpasses the uptime bound) or 2 (if the broiler's cumulative occupancy surpasses the uptime bound).

## Input

The first line contains two integers **j** and **T** (1 ≤ j ≤ 200000, 1 ≤ T ≤ 1000000000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the required minutes of the `JOB` in appliance 1 and appliance 2.

## Output

Print a single line: `JOB i` (a `JOB` whose slack check fails) or `LOAD c` (an appliance **c** whose cumulative occupancy surpasses the available uptime).

## Examples

### Example 1

**Input**
```
3 100
70 60
2 2
3 4
```

**Output**
```
JOB 1
```

### Example 2

**Input**
```
4 150
50 1
50 1
50 1
50 1
```

**Output**
```
LOAD 1
```

## Note

In Example 1, for `JOB` 1, if it starts at time 0, its oven completion time is 70. The latest possible moment it must enter the broiler to finish by the 100-minute deadline is 100 - 60 = 40. The slack between oven completion (70) and latest broiler entry (40) is 40 - 70 = -30, which is strictly negative. Thus, `JOB 1` proves the deadline is impossible.

In Example 2, no single `JOB` has negative slack. However, if we pack every recipe's required time for appliance 1 into a single continuous block, the cumulative occupancy is 50 + 50 + 50 + 50 = 200. This surpasses the 150-minute maximum available uptime of the oven, so `LOAD 1` is the certificate.
</STATEMENT>
<RATIONALE>
The explicit arithmetic shortcuts `p1 + p2 > T` and `T - sum(p) < 0` were removed. The conditions were rewritten using the concepts of "slack" (latest start minus earliest completion) and "cumulative occupancy" surpassing maximum uptime. This forces the model to interpret these domain concepts and derive the correct inequalities rather than recognizing the one-pass pattern directly from the text.
</RATIONALE>
<PRESERVED_ANSWER>
The slack condition mathematically evaluates to `(T - p2) - p1 < 0`, which simplifies exactly to the original `p1 + p2 > T`, and the occupancy check evaluates to `sum(p) > T`, perfectly preserving the original failure modes.
</PRESERVED_ANSWER>

</PRESERVED_CLASS>
