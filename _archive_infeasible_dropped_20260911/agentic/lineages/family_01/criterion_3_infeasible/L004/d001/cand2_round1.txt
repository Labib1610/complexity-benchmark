<STATEMENT>
# Problem C — Proof of Impossibility

Time limit: 2 s
Memory limit: 256 MB

The factory's automated rostering system operates in three stages. In the first stage, it gathers scheduling constraints into a centralized database. In the second stage—which is the component you must implement—the system must process a roster that is already known to be hopeless. The factory has only two shifts, 1 and 2. Your job is not to assign shifts; rather, it is to generate a certificate of impossibility to pass to the third stage. The third stage will then consume this certificate to automatically trigger an expansion request for a third shift.

The factory employs a certain headcount of workers. A minimum of three workers are required to operate the machinery, while the building's maximum occupancy strictly limits the headcount to two thousand workers. The database logs a number of directed conflict reports. There are at least three reports, and to prevent database overload, the system enforces a hard cap of two hundred thousand reports (or the maximum possible number of unique pairs, if smaller). 

Every conflict report is processed as a directed arc from the worker with the smaller ID to the worker with the larger ID. Thus, a report involving workers `u` and `v` always creates an arc `min(u,v) → max(u,v)`. 

It is guaranteed that the conflict database contains at least one impossible group. A valid certificate of impossibility is a specific pattern of exactly three workers `a`, `b`, and `c` (where `a < b < c`) such that the database contains all three of the following directed arcs:
- `a → b`
- `a → c`
- `b → c`

Any such group proves two shifts cannot suffice and serves as a valid certificate. You must output one such group.

## Input
The first line contains two integers: the headcount and the number of conflict reports.
Each of the next lines contains two integers `u` and `v` — indicating a conflict report involving these two workers.
It is guaranteed that at least one valid certificate exists.

## Output
Print three integers `a`, `b`, and `c` on one line with `a < b < c` such that the required directed arcs exist between them. Output the lexicographically smallest such triple (smallest `a`; ties broken by smallest `b`; then smallest `c`).

## Example 1
Input:
```
4 5
1 2
1 3
2 3
2 4
3 4
```
Output:
```
1 2 3
```

## Example 2
Input:
```
5 6
1 2
1 4
2 4
3 4
3 5
4 5
```
Output:
```
1 2 4
```
</STATEMENT>
<RATIONALE>
The problem was reframed to explicitly require a directed transitive triangle (`a→b`, `a→c`, `b→c`) while defining the direction of every input edge to strictly flow from the smaller ID to the larger ID. This forces models to carefully implement the `min(u,v) → max(u,v)` logic rather than blindly treating the input as an undirected graph or a standard directed graph. Models that pattern-match the directed triangle requirement but fail to apply the ID-based direction rules will miss valid certificates. Additionally, numeric bounds were rewritten as physical scenario constraints (e.g., maximum occupancy of 2000) to penalize models that cannot extract indirect bounds.
</RATIONALE>
<PRESERVED_ANSWER>
Because every input edge is explicitly directed from the smaller ID to the larger ID, the required directed pattern (`a→b`, `a→c`, `b→c` with `a < b < c`) is logically identical to an undirected triangle between `a`, `b`, and `c`, meaning the lexicographically smallest valid triple remains exactly the same for all possible inputs.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The core computational task remains finding a 3-clique (triangle) in a graph to prove 3-colorability infeasibility, which preserves its true complexity class and intended $O(nm/64)$ bitset algorithm.
</PRESERVED_CLASS>
