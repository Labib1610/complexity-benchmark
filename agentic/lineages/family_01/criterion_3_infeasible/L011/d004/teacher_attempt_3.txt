# Dual-Core Scheduling Conflict

Time limit: 2 s
Memory limit: 256 MB

A software system manages a set of concurrent tasks, attempting to divide them between two execution cores. Certain pairs of tasks attempt to access the same exclusive hardware register, meaning they cannot be assigned to the same core.

The system is currently failing to divide the tasks. Diagnostics indicate this is caused by a specific local failure: a group of exactly three tasks, let's call them X, Y, and Z, where X cannot share a core with Y, Y cannot share a core with Z, and Z cannot share a core with X. Because of these three overlapping restrictions, they cannot be split across only two cores.

Your objective is to isolate one such group of three tasks. If multiple such groups exist, you must identify the one with the lowest hardware trace. For a group consisting of task IDs $a, b,$ and $c$ (sorted such that $a < b < c$), the hardware trace is calculated as $a \cdot 10^8 + b \cdot 10^4 + c$.

## Input
The first line of the input contains two integers $n$ and $m$, representing the number of tasks and the number of recorded register conflicts. 
The number of tasks $n$ is at least 3. The system limits the maximum number of tasks by allocating exactly 4 kilobytes of memory per task out of a strict 8,000-kilobyte total pool.
The number of recorded conflicts $m$ is at least 3. The conflict log file is capped at exactly 1,000,000 bytes, where each conflict record takes exactly 5 bytes. The number of conflicts will not exceed the maximum possible number of valid task pairings.
The tasks are assigned integer IDs from $1$ to $n$.

Each of the subsequent $m$ lines contains two distinct integers $u$ and $v$ ($1 \le u, v \le n$), indicating that task $u$ and task $v$ cannot share a core.

The provided records are guaranteed to contain at least one group of three tasks that restrict each other as described.

## Output
Output a single line containing three space-separated integers $a$, $b$, and $c$ ($a < b < c$) representing the IDs of the three tasks in the group. You must output the configuration that yields the minimum hardware trace.

## Example 1
Input:
```
4 5
1 2
1 3
2 3
2 4
3 4
```
Output:
```
1 2 3
```

## Example 2
Input:
```
5 6
1 2
1 4
2 4
3 4
3 5
4 5
```
Output:
```
1 2 4
```

<RATIONALE>
I replaced the explicit mention of "mutual incompatibility" and "every pair" with a structural description of three tasks (X, Y, and Z) where X conflicts with Y, Y with Z, and Z with X. This forces the model to deduce the underlying structure rather than relying on keywords. I also encoded the numeric bounds as physical system limits (memory pools and log file sizes) so the model must derive the maximum values of n and m through arithmetic.
</RATIONALE>
<PRESERVED_ANSWER>
The logical requirement to find three tasks that all conflict with each other is mathematically identical to finding a 3-cycle in the conflict graph, and the trace formula for tie-breaking is exactly the same, ensuring identical outputs.
</PRESERVED_ANSWER>

The underlying task requires finding a 3-cycle in an undirected graph, which remains solvable in the exact same time complexity by iterating over edges and checking shared neighbors.
</PRESERVED_CLASS>
