<STATEMENT>
# Cryptographic Shard Allocation

Time limit: 2 s   Memory limit: 256 MB

A distributed ledger consists of $n$ distinct storage nodes. The system provides three tier levels for these nodes, designated by the integers 1, 2, and 3.

Each node $i$ (where $1 \le i \le n$) must be assigned a tier level $t_i \in \{1, 2, 3\}$.

Security audits have generated $m$ isolation constraints to prevent data correlation attacks. Each constraint specifies two nodes $u$ and $v$ whose assigned tier levels must satisfy the condition that their product $t_u \times t_v$ is not a perfect square. (An integer is considered a perfect square if it can be expressed as $k^2$ for some integer $k$).

The constraints can form complex, interlocking dependencies. Your solution must correctly process any configuration of constraints within the specified limits, verifying whether a valid allocation is possible or not.

You must determine whether it is feasible to assign a tier level to every node such that all $m$ constraints are simultaneously satisfied. If a valid assignment is possible, you must provide one. You only need to supply one valid assignment, even if multiple are possible.

## Input
The first line contains two integers $n$ and $m$ — the total number of nodes and the number of constraints ($1 \le n \le 40$, $0 \le m \le n(n-1)/2$).
Each of the subsequent $m$ lines contains two integers $u$ and $v$, indicating a constraint that the tier levels for node $u$ and node $v$ must satisfy the condition that $t_u \times t_v$ is not a perfect square.

## Output
If it is impossible to assign tier levels to all nodes such that every constraint is satisfied, print a single line containing `NO`.
If it is possible, print `YES` on the first line. On the second line, print $n$ integers $t_1, t_2, \dots, t_n$ separated by spaces, where each $t_i \in \{1, 2, 3\}$ indicates the tier assigned to node $i$. You only need to supply one valid assignment, even if multiple are possible.

## Example 1
Input:
```
4 5
1 2
1 3
2 3
1 4
2 4
```
Output:
```
YES
1 2 3 3
```

## Example 2
Input:
```
4 6
1 2
1 3
1 4
2 3
2 4
3 4
```
Output:
```
NO
```

<RATIONALE>
The problem was completely reframed from module environments to a cryptographic ledger scenario. The core inequality constraint (`|e_u - e_v| >= 1`) was replaced with a mathematically equivalent non-linear property (`t_u * t_v` is not a perfect square). Because the domain is restricted to `{1, 2, 3}`, a product is a perfect square if and only if the two values are identical. This forces the model to either deduce the true nature of the constraint and map it back to graph coloring, or write a naive constraint satisfaction solver that will lack degree-based pruning and Time Limit Exceed.
</RATIONALE>
<PRESERVED_ANSWER>
For values in {1, 2, 3}, the product of two values is a perfect square (1, 4, or 9) if and only if the values are equal; therefore, requiring the product to not be a perfect square is exactly equivalent to requiring the values to be distinct, preserving all valid assignments from the seed.
</PRESERVED_ANSWER>
