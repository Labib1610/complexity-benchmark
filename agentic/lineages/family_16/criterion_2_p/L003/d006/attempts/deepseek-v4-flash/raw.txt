We need to choose an ordering of the tiles to minimize the maximum possible path cost chosen by an adversary who maximizes the cost.

Let’s first see what a path looks like. The adversary starts at `(1, 1)` and ends at `(2, j)`, moving only right or down. A path will go right for some columns at the top row and then down once at some column `k` and then continue right on the bottom row.

So for a fixed ordering of tiles:

If the adversary switches from top to bottom at column `k` (1-indexed), the cost is:

```
cost(k) = sum of top values of tiles 1..k + sum of bottom values of tiles k..j
```

Because the starting at `(1,1)` includes tile 1 top, and going down at column `k` means tile `k` bottom is visited tooickle.

We want to minimize `max_k cost(k)`.  

For a given order, cost(k) can be written as:

```
cost(k) = (sum_top_1_to_k + sum_bottom_k_to_j)
```

Let `total_sum = sum(all top) + sum(all bottom)` for all tiles.  
Then:

`sum_top_1_to_k + sum_bottom_k_to_j = sum_top_1_to_k + sum_bottom_1_to_j - sum_bottom_1_to_{k-1}`  

Let’s rewrite:

```
cost(k) = sum_top_1_to_k + (total_bottom - sum_bottom_1_to_{k-1})
        = total_bottom + (sum_top_1_to_k - sum_bottom_1_to_{k-1})
```

Notice:

- For k=1:  sum_top_1 + total_bottom - sum_bottom_0 = top_1 + total_bottom
- For k=j:  total_top + bottom_j

Instead of summing over top prefix and bottom suffix, we can view each tile's contribution difference.

Consider the difference `d = p1 - p2` for each tile. When ordering, each tile when passed on top contributes `p1`, when passed on bottom contributes `p2`. The adversary’s path switches once.

The cost is:

```
cost(k) = sum_top_1_to_k + sum_bottom_k_to_j
```

We can write it as:

```
cost(k) = (sum_top_1_to_k - sum_bottom_1_to_k) + sum_bottom_1_to_j  + p2_k
```

But simpler:
  
Let `S = total_top + total_bottom`.  
We have:

`cost(k) = S - (sum_bottom_1_to_{k-1} + sum_top_{k+1}_to_j)`

So maximizing path is minimizing sum of omitted cells. But that’s messy.

Better known trick:  
For each tile i, define `a_i = p1_i`, `b_i = p2_i`.  
`cost(k) = (a_1 + ... + a_k) + (b_k + ... + b_j)`  
= `(a_1 + ... + a_k) + (b_k + ... + b_j) + 0`  
We can rewrite as constant + prefix of `(a_i - b_i)`:

Let prefix sum `Pref[i] = sum_{t=1..i} (a_t - b_t)`.  
Let total_bottom_sum = `B = sum b_i`.  
Then:
- For k from 1 to j:  
`cost(k) = (sum_{t=1..k} a_t) + (sum_{t=k..j} b_t)`  
`= (sum_{t=1..k} a_t) + (B - sum_{t=1..k-1} b_t)`  
`= B + sum_{t=1..k} a_t - sum_{t=1..k-1} b_t`  
`= B + (sum_{t=1..k} (a_t - b_t)) + b_k`  
Wait: Let’s do it carefully:

`sum_{t=1..k} a_t - sum_{t=1..k-1} b_t`  
= `(a_k - b_k) + sum_{t=1..k-1}(a_t - b_t)`  
= `Pref[k]` is `sum_{t=1..k}(a_t-b_t)`.

We have:

`sum_{t=1..k} a_t - sum_{t=1..k-1} b_t`  
= `(sum_{t=1..k} a_t - sum_{t=1..k} b_t) + b_k`  
= `Pref[k] + b_k`.

Thus:

```
cost(k) = B + Pref[k] + b_k
```

Where `Pref[k] = sum_{t=1..k}(a_t - b_t)`.

We need to order tiles to minimize `max_k (B + Pref[k] + b_k)`.

Since `B` is constant over ordering, minimizing `max_k (Pref[k] + b_k)` is the key.

Let’s define for each tile:  
`x_i = a_i - b_i`  
`b_i` is also known.

We need to arrange tiles so that prefix sums of `x_i` plus current `b_i` never get too large.

### Key insight:
We can reorder such that we “spread” the negative `x_i` earlier to keep prefix sums low.

So `Pref[k] + b_k = sum_{t=1..k-1} (a_t - b_t) + a_k`.

That’s exactly the sum of top values up to k, minus bottom values before k... It's basically cost formula.

Known solution: sort by `p1 + p2`? Let's check known result:  
This is reminiscent of problem “Grid Path Minimax”. The optimal strategy is to sort by `p1 - p2` ascending BB. It is a known fact that for minimizing maximum prefix sum of `(a_i - b_i) + b_i`, sort by `a_i + b_i`? Let’s derive.

We have `cost(k) = B + Pref[k] + b_k`.  
`Pref[k] = sum_{t≤k} (a_t-b_t)`.

Define `c_i = a_i - b_i`.  
Then `Pref[k] + b_k = sum_{t<k} c_t + a_k`. Because `Pref[k] + b_k = sum_{t≤k} c_t + b_k = sum_{t<k} c_t + (c_k + b_k) = sum_{t<k} c_t + a_k`.

So `cost(k) = B + sum_{t<k} c_t + a_k`.

Now, for each k, we add `a_k` plus previous sum of `c`. That means if we put tiles with large `c` early, prefix c grows fast, increasing future costs. So we want small `c` first. Also if `c` is equal, we prefer smaller `a_k`? Because `a_k` appears directly at its position.

Thus sort by `c = a-b` ascending, and if tie, by `a` ascending.

Let's verify with example 1:
(3,2): c=1, a=3  
(2,4): c=-2, a=2  
(1,3): c=-2, a=1  

Sort by c asc, then by a:  
(1,3) c=-2 a=1, (2,4) c=-2 a=2, (3,2) c=1 a=3  
Order: (1,3), (2,4), (3,2)  
B=9  
Compute:  
k=1: Pref=-2, b=3 => -2+3=1  
k=2: Pref=-4, b=4 => -4+4=0  
k=3: Pref=-3, b=2 => -3+2=-1  
Max=1 ⇒ total=10. Good.

Example with all equal: (2,2) c=0, a=2, b=2  
Sorting stays any order.  
B=6, Pref all 0, Pref+b=2 each => max=2 => total=8, matches.

Thus sorting key: `(a-b, a)` ascending.

Now implement.

Be careful with size: j up to 2e5.

Complexity O(j log j).

Now produce code.

```python
import sys

def solve():
    input = sys.stdin.readline
    j = int(input())
    tiles = []
    total_bottom = 0
    for _ in range(j):
        p1, p2 = map(int, input().split())
        tiles.append((p1 - p2, p1, p2))
        total_bottom += p2
    
    # Sort by difference, then by p1
    tiles.sort(key=lambda x: (x[0], x[1]))
    
    max_val = -10**18
    pref = 0
    for diff, a, b in tiles:
        pref += diff
        val = pref + b
        if val > max_val:
            max_val = val
    
    print(total_bottom + max_val)

if __name__ == "__main__":
    solve()
```
