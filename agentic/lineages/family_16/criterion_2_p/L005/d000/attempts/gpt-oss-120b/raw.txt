**Solution Explanation**

For every asset we know

* drafting time `a`
* rendering time `b`

Both machines work on **exactly one** asset at a time and every asset must be drafted
before it can be rendered.
All assets have to be processed in the *same* order on the two machines.
We have to choose this order so that the finishing time of the last asset is minimal.

The problem is the classical *two‑machine flow shop* makespan problem.
For two machines the optimal order is given by **Johnson’s rule**.



--------------------------------------------------------------------

#### 1.   Johnson’s rule for two machines  

For an asset `i`

```
a_i = drafting time
b_i = rendering time
```

*If `a_i ≤ b_i`* the asset should be placed **as early as possible**.  
*If `a_i > b_i`* the asset should be placed **as late as possible**.

More precisely  

* collect all assets with `a_i ≤ b_i`, sort them by increasing `a_i`
* collect all assets with `a_i >  b_i`, sort them by decreasing `b_i`
* concatenate the two lists (first the early part, then the late part)

The obtained sequence is optimal, i.e. it gives the smallest possible
completion time of the last rendering.

*Proof sketch*  
Consider any optimal schedule.
Take the leftmost asset `x` with `a_x > b_x`.  
If there exists an asset `y` left of `x` with `a_y ≤ b_y`,
exchange `x` and `y`.  
The exchange never increases the makespan (a short, easy‑to‑render job
goes earlier, a long drafting job goes later). Repeating the exchange
moves all assets with `a_i > b_i` to the right side, preserving order
within each group. Finally the assets of the first group can be sorted
by increasing `a_i` without worsening the makespan (pairwise
interchange argument). The same holds for the second group with
decreasing `b_i`. ∎



--------------------------------------------------------------------

#### 2.   Computing the makespan of a given order  

```
draft = 0          # time when drafting machine becomes free
render = 0         # time when rendering machine becomes free

for (a, b) in order:
        draft += a                     # drafting of this asset finishes
        render = max(render, draft) + b   # it can start rendering only after both machines are free
```

After the loop `render` is the finishing time of the last asset.



--------------------------------------------------------------------

#### 3.   Algorithm
```
read j
read all pairs (a, b)

front = []   # a ≤ b
back  = []   # a >  b
for each pair:
        if a <= b:   front.append((a,b))
        else:        back.append((a,b))

front.sort(key = lambda x: x[0])          # increasing a
back.sort(key  = lambda x: x[1], reverse=True)   # decreasing b

order = front + back

draft = render = 0
for a, b in order:
        draft += a
        render = max(render, draft) + b

print(render)
```

--------------------------------------------------------------------

#### 4.   Correctness Proof  

We prove that the algorithm outputs the minimal possible finishing time.

---

##### Lemma 1  
For any two assets `i` and `j` with `a_i ≤ b_i` and `a_j ≤ b_j`,
processing `i` before `j` (i.e. ordering by non‑decreasing `a`) does not
increase the makespan compared with the opposite order.

**Proof.**  
Consider the two possible orders, all other assets unchanged.

```
order 1: ... i ... j ...
order 2: ... j ... i ...
```

Let `T` be the time when the drafting of the first of the two assets finishes.
In order 1 this time is `T + a_i`, in order 2 it is `T + a_j`.  
Because `a_i ≤ a_j`, drafting finishes earlier in order 1.
Rendering of the first asset can start at `max(render_free, T + a_i)` and lasts
`b_i`. Since `a_i ≤ b_i`, we have `T + a_i ≤ T + b_i`, therefore the rendering
machine will be idle at most as long in order 1 as in order 2.
Consequently the finishing time of the second asset (and of the whole schedule)
is not larger in order 1. ∎



##### Lemma 2  
For any two assets `i` and `j` with `a_i > b_i` and `a_j > b_j`,
processing `i` after `j` (i.e. ordering by non‑increasing `b`) does not
increase the makespan.

**Proof.** Symmetric to Lemma&nbsp;1, exchanging the roles of drafting and rendering
and using `b_i ≥ a_i`. ∎



##### Lemma 3  
There exists an optimal schedule in which all assets with `a ≤ b` appear
before all assets with `a > b`.

**Proof.**  
Take an optimal schedule with the smallest possible number of
“inversions”, i.e. pairs `(x, y)` where `x` is before `y` but
`a_x > b_x` and `a_y ≤ b_y`.  
If such a pair exists, exchange `x` and `y`.  
By Lemma&nbsp;1 and Lemma&nbsp;2 the makespan does not increase, while the number of
inversions decreases – contradiction. Hence an optimal schedule with no
inversions exists, i.e. all `a ≤ b` assets precede all `a > b` assets. ∎



##### Lemma 4  
Within the first group (`a ≤ b`) sorting by increasing `a` keeps the schedule optimal.
Within the second group (`a > b`) sorting by decreasing `b` keeps the schedule optimal.

**Proof.** Directly from Lemma&nbsp;1 (first group) and Lemma&nbsp;2 (second group). ∎



##### Theorem  
The order produced by the algorithm (Johnson’s rule) yields the minimum
possible finishing time of the last rendering.

**Proof.**  
By Lemma&nbsp;3 there exists an optimal schedule where the two groups are
separated.  
By Lemma&nbsp;4 each group can be internally ordered as the algorithm does
without worsening the makespan.  
Therefore the algorithm constructs an optimal schedule.  
The makespan computed in the second phase is exactly the finishing time of
that schedule, thus minimal. ∎



--------------------------------------------------------------------

#### 5.   Complexity Analysis  

*Splitting into two groups* – **O(j)**  
*Sorting* – `O(j log j)` (dominant step)  
*Simulation* – **O(j)**  

Memory consumption: storing all pairs – **O(j)**.

Both limits satisfy `j ≤ 200 000` and the 1 s time limit.

#### 6.   Reference Implementation  (Python 3)

```python
import sys

def solve() -> None:
    data = sys.stdin.buffer.read().split()
    if not data:
        return
    it = iter(data)
    n = int(next(it))
    front = []   # a <= b
    back = []    # a >  b
    for _ in range(n):
        a = int(next(it))
        b = int(next(it))
        if a <= b:
            front.append((a, b))
        else:
            back.append((a, b))

    front.sort(key=lambda x: x[0])          # increasing a
    back.sort(key=lambda x: x[1], reverse=True)   # decreasing b

    draft = 0
    render = 0
    for a, b in front:
        draft += a
        render = max(render, draft) + b
    for a, b in back:
        draft += a
        render = max(render, draft) + b

    sys.stdout.write(str(render))

if __name__ == "__main__":
    solve()
```

conforms to the required input / output format.
