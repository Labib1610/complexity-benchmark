# Problem B — Battery Testing Sequence

Time limit: 1 s   Memory limit: 256 MB

## Description

You are testing a prototype power battery using **j** different diagnostic applications. 

To evaluate the battery's performance, you track two metrics throughout the testing sequence: the "Internal Load Count" (ILC) and the "Total Generated Power" (TGP). Both the ILC and the TGP start at 0.

Each application has two parameters: a power requirement **p1** and a power generation **p2**.
When you run an application, the following two steps happen in exact order:
1. The application requires **p1** units of power. The ILC increases by **p1**. However, the ILC can never exceed the current TGP (which represents the total power generated by all previously run applications). If the new ILC is strictly greater than the current TGP, the ILC is immediately capped to equal the current TGP.
2. The application then generates **p2** units of power. The TGP increases by **p2**.

You must run all **j** applications exactly once, in a single sequence of your choosing.

The overall "inefficiency rating" of your test sequence is defined as the total power requirements of all applications (the sum of all **p1** values), plus the total power generated by all applications (the sum of all **p2** values), minus the final ILC after all **j** applications have finished.

Find an execution order for the applications that makes this inefficiency rating as small as possible. Report this minimum possible inefficiency rating.

## Input

The first line contains a single integer **j** (1 ≤ j ≤ 200000).
Each of the next **j** lines contains two integers **p1** and **p2** (1 ≤ p1, p2 ≤ 1000000): the power requirement and the power generation of an application.

## Output

Print a single integer: the minimum possible inefficiency rating.

## Examples

### Example 1

**Input**
```
3
3 2
2 4
1 3
```

**Output**
```
10
```

### Example 2

**Input**
```
1
5 3
```

**Output**
```
8
```

### Example 3

**Input**
```
3
2 2
2 2
2 2
```

**Output**
```
8
```

## Note

In Example 1, an optimal arrangement runs the applications in the order of the 3rd, 2nd, and 1st from the input.
- The total power requirement of all applications is $1 + 2 + 3 = 6$.
- The total power generation of all applications is $3 + 4 + 2 = 9$.
- Initially, ILC = 0 and TGP = 0.
- For the 3rd input application ($p1=1, p2=3$):
  - Step 1: ILC increases by 1 (to 1). The current TGP is 0. Since 1 > 0, ILC is capped at 0.
  - Step 2: TGP increases by 3 (to 3).
- For the 2nd input application ($p1=2, p2=4$):
  - Step 1: ILC increases by 2 (to 2). The current TGP is 3. Since 2 ≤ 3, ILC remains 2.
  - Step 2: TGP increases by 4 (to 7).
- For the 1st input application ($p1=3, p2=2$):
  - Step 1: ILC increases by 3 (to 5). The current TGP is 7. Since 5 ≤ 7, ILC remains 5.
  - Step 2: TGP increases by 2 (to 9).
- The final ILC is 5.
- The inefficiency rating is $6 + 9 - 5 = 10$.

<RATIONALE>
I replaced the standard "battery drains to zero and grid covers deficit" mechanic—which models easily map to the `max(0, state - p1) + p2` pattern of Johnson's rule—with an inverted state tracking system. This forces the models to evaluate a `min(ILC + p1, TGP)` structure, breaking their memorized flow-shop pattern matches while strictly preserving the sequential step-by-step narrative required by the gate.
</RATIONALE>
<PRESERVED_ANSWER>
The final ILC mathematically equals the total generated power minus the final battery level of the original formulation, making the new objective `sum(p1) + sum(p2) - ILC` algebraically identical to the seed's `sum(p1) + final_battery`, guaranteeing identical answers for all sequences.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
Because the tracking metrics are an exact algebraic substitution of the original state variables, the problem remains equivalent to a two-machine flow-shop scheduling problem optimally solvable in O(n log n) time.
</PRESERVED_CLASS>
<RISK>
Models might misinterpret whether the "current TGP" includes the power generated in Step 2 of the *current* application, though the text explicitly states "which represents the total power generated by all previously run applications" and the exact sequence of steps clarifies this.
</RISK>
