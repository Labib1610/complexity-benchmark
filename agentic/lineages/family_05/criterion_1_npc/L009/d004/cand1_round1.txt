<STATEMENT>
# Problem A — Collision-Free Allocation

Time limit: 5 s   Memory limit: 256 MB

## Description

A computing cluster has **k** processors, **k** memory banks, and **k** storage drives, each identified by integers 1 through **k**.

You are given a list of **t** possible tasks that can be executed on the cluster. Each task requires a specific combination of hardware: exactly one processor, exactly one memory bank, and exactly one storage drive. The **i**-th task in the list is represented by a triplet `(x, y, z)`, meaning it requires processor **x**, memory bank **y**, and storage drive **z**.

You must select exactly **k** tasks from the list to run simultaneously. To avoid hardware collisions, the selected set of tasks must be entirely mutually exclusive. Specifically, a selection of **k** tasks is strictly collision-free if and only if:
- No two selected tasks use the same processor.
- No two selected tasks use the same memory bank.
- No two selected tasks use the same storage drive.

Determine if it is possible to select exactly **k** tasks that form a strictly collision-free set. If it is possible, output one valid set of **k** tasks.

## Input

The first line contains two integers **k** and **t** (1 ≤ k ≤ 22, 0 ≤ t ≤ k·k·k): the number of components of each hardware type and the number of possible tasks.
Each of the next **t** lines contains three integers **x**, **y**, **z** (1 ≤ x, y, z ≤ k), representing a task that requires processor **x**, memory bank **y**, and storage drive **z**. No task is listed more than once.

## Output

If a strictly collision-free set of exactly **k** tasks exists, print `YES` on the first line, then print **k** lines, each containing the three members `x y z` of one selected task. Any valid set is accepted; the tasks may be printed in any order.

If no such set exists, print `NO`.

## Examples

### Example 1

**Input**
```
2 3
1 1 1
1 2 2
2 2 2
```

**Output**
```
YES
1 1 1
2 2 2
```

### Example 2

**Input**
```
2 2
1 1 1
2 1 2
```

**Output**
```
NO
```

### Example 3

**Input**
```
1 1
1 1 1
```

**Output**
```
YES
1 1 1
```

## Note

In Example 2, both possible tasks require processor 1. If we try to select exactly 2 tasks from this list, they will both use processor 1, which violates the rule that no two selected tasks can use the same processor. Thus, a strictly collision-free set of 2 tasks cannot be formed.
</STATEMENT>
<RATIONALE>
I replaced the explicit "contains every number from 1 to k exactly once" constraints with "no two selected tasks use the same..." constraints. Because the problem requires selecting exactly k tasks from a domain of k hardware IDs, the Pigeonhole Principle ensures this is mathematically identical to an exact cover. However, this shifts the surface framing from Exact Cover/3D Matching to Maximum Independent Set, forcing models to deduce the dimension-wise search space reduction rather than having it handed to them by the wording.
</RATIONALE>
<PRESERVED_ANSWER>
Selecting exactly k items with no collisions from a set of k possible IDs mathematically requires using every ID exactly once, meaning the set of valid configurations is functionally identical for every input.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem remains exactly 3-Dimensional Matching, which is NP-complete.
</PRESERVED_CLASS>
<RISK>
Models might misinterpret "no two selected tasks use the same processor" as allowing fewer than k processors to be used overall, but the strict requirement to "select exactly k tasks" prevents this from changing the logic.
</RISK>

</METHOD_NAME>
<METHOD_DESCRIPTION>
Replace the explicit exact-cover constraint ("uses 1..k exactly once") with a collision-free constraint ("no two items share an ID"). By the Pigeonhole Principle, selecting k items from a domain of size k with no collisions forces an exact cover. This primes models to formulate the problem as an Independent Set or naive subset search (which TLEs for large t) rather than leveraging the dimension-wise exact cover structure (DLX/backtracking), testing their ability to deduce the underlying search space reduction themselves.
</METHOD_DESCRIPTION>
