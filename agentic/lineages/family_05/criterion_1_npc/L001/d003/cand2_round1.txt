<STATEMENT>
# Problem A — Crew Assembly

Time limit: 5 s   Memory limit: 256 MB

## Description

To execute a complex mission, you must synchronize three separate resource categories. Each category consists of identically sized pools of exactly **k** entities:
- Operators (numbered 1 to **k**)
- Hardware units (numbered 1 to **k**)
- Mission phases (numbered 1 to **k**)

A single deployment consists of exactly one Operator, one Hardware unit, and one Mission phase. However, strict certification rules dictate that only a specific subset of these three-part deployments are authorized for use. You are provided with a complete catalog of all authorized deployments.

Your objective is to extract an operational roster from this catalog. A valid roster must contain exactly **k** authorized deployments. Furthermore, zero overlap is permitted across the chosen deployments: every Operator, every Hardware unit, and every Mission phase must appear exactly once in the entire roster.

Determine whether such a roster can be formed. If successful, output one such set of **k** deployments.

## Input

The first line contains two integers **k** and **t**. The pool size **k** is at least 1 and cannot exceed the command center's physical limit of 22 active operational sectors. The integer **t** represents the number of authorized deployments in the catalog, ranging from an empty catalog up to the theoretical maximum of all possible combinations for a pool of size **k**.

This is followed by **t** lines. Each line provides three integers **x**, **y**, and **z**, indicating that a deployment uniting Operator **x**, Hardware unit **y**, and Mission phase **z** is authorized. The integers **x**, **y**, and **z** are guaranteed to correspond to valid entity identifiers (from 1 to **k**) in their respective pools. No deployment is listed more than once.

## Output

If a non-overlapping roster of **k** deployments exists, print `YES` on the first line. Then print **k** lines, each containing the three integers `x y z` of a deployment included in your roster. You may print the deployments in any order.

If it is impossible to form such a roster, print `NO`.

## Examples

### Example 1

**Input**
```
2 3
1 1 1
1 2 2
2 2 2
```

**Output**
```
YES
1 1 1
2 2 2
```

### Example 2

**Input**
```
2 2
1 1 1
2 1 2
```

**Output**
```
NO
```

### Example 3

**Input**
```
1 1
1 1 1
```

**Output**
```
YES
1 1 1
```

## Note

In Example 2, both authorized deployments require Hardware unit 1. A roster of exactly 2 deployments cannot be formed without reusing Hardware unit 1, which violates the zero-overlap requirement.

The explicit inequalities `1 ≤ k ≤ 22` and `0 ≤ t ≤ k·k·k` have been replaced with natural language descriptions of the scenario's physical limits and mathematical bounds. This forces models to parse and comprehend the text to deduce the input constraints, disrupting surface-level pattern matching that relies on bare mathematical inequalities to trigger exact-cover or bitmask DP algorithms.
</RATIONALE>

The requirements for valid deployments and the zero-overlap constraints are mathematically identical to the original problem, ensuring that the same sets of inputs produce the exact same valid outputs.
