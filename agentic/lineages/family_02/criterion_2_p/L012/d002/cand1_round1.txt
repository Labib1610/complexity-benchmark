<STATEMENT>
# Redundancy Link Configuration

Time limit: 1 s   Memory limit: 256 MB

## Description

The system configuration pipeline operates in three stages. First, a parser transforms complex user requirements into a standardized intermediate format concerning $n$ sensors, each to be assigned to either OPERATED or BYPASSED status before the run. This format consists of $m$ dependency links.

Each link specifies exactly two potential operational modes. A mode consists of a sensor identifier and the required status (OPERATED or BYPASSED) for that sensor. The link highlights a coverage gap: the system is vulnerable if it is configured in a way that provides neither the first mode nor the second mode. 

In the second stage—which your program must implement—you evaluate this intermediate format. Your task is to determine whether a single global OPERATED/BYPASSED assignment for all $n$ sensors exists that successfully covers all gaps. If a valid configuration exists, report one. Otherwise, report that the links are mutually contradictory.

Finally, in the third stage, a downstream controller will read your output and physically actuate the sensors.

## Input
The first line contains two integers $n$ and $m$ ($1 \le n \le 10^5$, $0 \le m \le 2 \cdot 10^5$).
Each of the next $m$ lines contains two non-zero signed integers $l_1$ and $l_2$, with $|l_i| \le n$. These represent the two modes for a dependency link. A positive integer $x$ specifies the mode where sensor $x$ is OPERATED, and a negative integer $-x$ specifies the mode where sensor $x$ is BYPASSED. A coverage gap occurs—rendering the system invalid—if the final configuration provides neither the mode specified by $l_1$ nor the mode specified by $l_2$.

## Output
If no valid assignment exists, print a single line `NO`.
Otherwise, print `YES` on the first line. On the second line, print $n$ integers $s_1, s_2, \dots, s_n$ (each in $\{0, 1\}$) forming any valid assignment, where $1$ denotes OPERATED and $0$ denotes BYPASSED.

## Example 1
Input:
```
2 2
1 2
-1 -2
```
Output:
```
YES
1 0
```

## Example 2
Input:
```
1 2
1 1
-1 -1
```
Output:
```
NO
```

## Note
Multiple valid assignments may exist; any one is accepted. The same mode may appear in multiple links.
</STATEMENT>
<RATIONALE>
The explicit boolean OR framing ("at least one of its two conditions is met") was replaced with a negated NOR framing ("provides neither... nor... rendering the system invalid"). This forces models to deduce the underlying logical clauses via De Morgan's laws rather than relying on surface-level keyword matching to trigger their 2-SAT templates.
</RATIONALE>
<PRESERVED_ANSWER>
Forbidding the state where neither condition is met is logically equivalent to requiring that at least one condition is met, so the set of valid configurations for any input remains identical.
</PRESERVED_ANSWER>
