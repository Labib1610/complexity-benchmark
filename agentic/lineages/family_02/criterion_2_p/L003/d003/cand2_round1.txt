<STATEMENT>
# Phase 3: Deployment Planner

Time limit: 1 s   Memory limit: 256 MB

## Description
You are managing the deployment of $n$ microservices. Each microservice must be allocated to exactly one of two environments: the Primary Environment (represented by 1) or the Secondary Environment (represented by 0).

The architecture includes $m$ fallback rules to ensure reliability. Each rule defines a dependency between two target states. A target state is represented by a non-zero integer $v$. The absolute value $|v|$ identifies the microservice. A positive $v$ indicates a target of placing microservice $|v|$ in the Primary Environment. A negative $v$ indicates a target of placing microservice $|v|$ in the Secondary Environment.

A fallback rule dictates an operational response: if the deployment fails to achieve the first target state, it becomes strictly obligated to achieve the second target state. Symmetrically, failing to achieve the second target state forces the system to achieve the first. (If the first target state is successfully achieved, the fallback is not triggered, placing no restriction on the second; similarly, achieving the second places no restriction on the first). Your task is to determine whether there exists a global allocation—assigning every microservice to either the Primary or Secondary environment—such that all fallback rules are satisfied.

## Input
The first line contains two integers $n$ and $m$, representing the number of microservices and the number of fallback rules. The system mandates a minimum of one microservice, with a hardware limit capping the registry at one hundred thousand microservices. The rule engine can be empty, or it can hold up to two hundred thousand rules.

Each of the following $m$ lines provides a rule as two non-zero integers $l_1$ and $l_2$. The magnitude of each integer guarantees a valid microservice ID (from one up to $n$). A positive $l_i$ sets the Primary Environment as the target state for microservice $|l_i|$; a negative $l_i$ sets the Secondary Environment as the target state for microservice $|l_i|$.

## Output
If no valid global allocation exists, print a single line containing `NO`.
Otherwise, print `YES` on the first line. On the second line, print $n$ integers $s_1, s_2, \dots, s_n$ separated by spaces. Print $s_i = 1$ if microservice $i$ is allocated to the Primary Environment, and $s_i = 0$ if it is allocated to the Secondary Environment. Any valid allocation is accepted.

## Example 1
Input:
```
2 2
1 2
-1 -2
```
Output:
```
YES
1 0
```

## Example 2
Input:
```
1 2
1 1
-1 -1
```
Output:
```
NO
```

## Note
Multiple valid allocations may exist; any one is accepted. The same microservice ID may appear in multiple rules, and even within the same rule (for example, a rule given as `3 3` simply means the system cannot miss this target, effectively mandating that specific state). If the rule engine is empty, any allocation is valid.
</STATEMENT>
<RATIONALE>
The description of the constraints was shifted from a disjunctive clause ("simultaneously fails to match both") to an implication-based operational rule ("if it fails to achieve the first, it must achieve the second"). This removes the direct textual cue that models were using to immediately map the problem to standard 2-CNF clauses. Additionally, numeric bounds were translated into system capacities following Strategy S07.
</RATIONALE>
<PRESERVED_ANSWER>
The logical requirement that failing condition A forces condition B (and vice versa) is logically equivalent to the original requirement that both conditions cannot simultaneously fail, preserving all valid allocations.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem remains exactly 2-SAT, as each rule establishes a pair of implications between two literals, which can be solved in linear time using strongly connected components.
</PRESERVED_CLASS>
<RISK>
Models might interpret the implication as an exclusive-or (XOR) requirement, but the parenthetical explicitly clarifies that achieving both states is valid and triggers no restrictions, eliminating this risk.
</RISK>
