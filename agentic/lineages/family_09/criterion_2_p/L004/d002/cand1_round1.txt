# Pipeline Stage 2: Safe Batch Selection

Time limit: 2 s   Memory limit: 256 MB

## Description

In our automated deployment pipeline, the process of deploying microservices to the testing environment is divided into three consecutive stages:

**Stage 1: Conflict Analysis.** A static analysis tool examines **n** available microservices (numbered 1 to **n**) and identifies **m** pairs that share a mutable database table. These are flagged as conflicting pairs. Due to the strict alternating request-response schema enforced by the system, the analyzer guarantees a specific structural property: if you were to trace any circular chain of conflicting microservices (a sequence of distinct microservices where each conflicts with the next, and the last conflicts with the first), the number of microservices in that chain will always be even.

**Stage 2: Safe Batch Selection (Your Task).** The deployment coordinator receives the list of microservices and the conflicting pairs from Stage 1. It must select exactly **k** distinct microservices to form a "safe batch." A batch is safe if absolutely no two microservices within it conflict with each other. You must determine if such a batch can be formed, and if so, output the selection. If multiple valid safe batches of size **k** exist, any one of them is accepted.

**Stage 3: Integration Testing.** The safe batch produced by Stage 2 is handed off to the container orchestration engine, which deploys them to an isolated cluster for performance testing.

Your software is only responsible for executing **Stage 2**. You will be given the output from Stage 1, and you must generate a valid batch selection to initiate Stage 3.

## Input

The first line contains three integers **n**, **m**, and **k** (1 ≤ n ≤ 100000, 0 ≤ m ≤ 400000, 1 ≤ k ≤ n).
The following **m** lines provide the conflict data from Stage 1. Each line contains two integers **u** and **v** (1 ≤ u, v ≤ n, u ≠ v), representing a conflicting pair of microservices. No pair is listed more than once. It is guaranteed that the conflict pairs adhere to the even-chain property described in Stage 1.

## Output

If a safe batch of exactly **k** microservices can be formed for Stage 3, print `YES` on the first line. On the second line, print the **k** distinct microservice numbers that form this batch, separated by spaces. If multiple safe batches of size **k** exist, any of them is accepted.

If it is impossible to form a safe batch of size **k**, print `NO`.

<RATIONALE>
The explicit "two camps" guarantee was an input property that trivially gave away the graph's bipartite nature, allowing models to immediately apply 2-coloring. Since removing this guarantee entirely would change the problem to NP-complete (violating Constraint 3), I re-presented the bipartite guarantee using its equivalent definition: the absence of odd cycles, described mechanically as "any circular chain... will always be even." This forces the model to mathematically deduce that the graph is bipartite before applying the intended P-time algorithm.
</RATIONALE>

The problem still asks for an independent set of size k, and the underlying conflict graph still possesses the exact same structural properties, ensuring all valid outputs remain valid.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The graph is still guaranteed to have no odd cycles, meaning it is bipartite; thus, finding a maximum independent set remains solvable in polynomial time via König's theorem and Hopcroft-Karp.
</PRESERVED_CLASS>
<RISK>
Models might fail to realize that "all circular chains are even" implies the graph is bipartite and instead attempt an NP-complete general independent set algorithm, leading to a Time Limit Exceeded error. However, the wording is mathematically unambiguous for a careful reader.
</RISK>
