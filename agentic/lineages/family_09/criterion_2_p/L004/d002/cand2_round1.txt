# Pipeline Stage 2: Safe Batch Selection

Time limit: 2 s   Memory limit: 256 MB

## Description

In our automated deployment pipeline, the process of deploying microservices to the testing environment is divided into three consecutive stages:

**Stage 1: Conflict Analysis.** A static analysis tool examines **n** available microservices (numbered 1 to **n**) and identifies **m** pairs that share a mutable database table. These are flagged as conflicting pairs. The system architecture imposes a strict dependency hierarchy. As a result of this hierarchy, the analyzer guarantees that the conflict network contains no odd-length feedback loops. Specifically, any sequence of three or more distinct microservices where each conflicts with the next, and the final microservice conflicts with the first, will always consist of an even number of microservices.

**Stage 2: Safe Batch Selection (Your Task).** The deployment coordinator receives the list of microservices and the conflicting pairs from Stage 1. It must select exactly **k** distinct microservices to form a "safe batch." A batch is safe if absolutely no two microservices within it conflict with each other. You must determine if such a batch can be formed, and if so, output the selection. If multiple valid safe batches of size **k** exist, any one of them is accepted.

**Stage 3: Integration Testing.** The safe batch produced by Stage 2 is handed off to the container orchestration engine, which deploys them to an isolated cluster for performance testing.

Your software is only responsible for executing **Stage 2**. You will be given the output from Stage 1, and you must generate a valid batch selection to initiate Stage 3.

## Input

The first line contains three integers **n**, **m**, and **k** (1 ≤ n ≤ 100000, 0 ≤ m ≤ 400000, 1 ≤ k ≤ n).
The following **m** lines provide the conflict data from Stage 1. Each line contains two integers **u** and **v** (1 ≤ u, v ≤ n, u ≠ v), representing a conflicting pair of microservices. No pair is listed more than once. It is guaranteed that the pairs adhere to the structural property described in Stage 1.

## Output

If a safe batch of exactly **k** microservices can be formed for Stage 3, print `YES` on the first line. On the second line, print the **k** distinct microservice numbers that form this batch, separated by spaces. If multiple safe batches of size **k** exist, any of them is accepted.

If it is impossible to form a safe batch of size **k**, print `NO`.

<RATIONALE>
The explicit "two-camp" guarantee was removed because it allowed models to immediately recognize the graph as bipartite and apply standard bipartite independent set algorithms. It was replaced with the mathematically equivalent property that the conflict network contains no odd-length cycles. This forces the model to deduce the bipartite nature of the graph from its cycle properties before it can recognize the problem as tractable.
</RATIONALE>
<PRESERVED_ANSWER>
The structural guarantee of the input graph remains exactly the same (bipartite), meaning any valid safe batch of size k in the original problem remains valid here.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem remains Maximum Independent Set on bipartite graphs, which is solvable in polynomial time via Hopcroft-Karp and König's theorem.
</PRESERVED_CLASS>
<RISK>
The definition of a cycle ("sequence of three or more distinct microservices where each conflicts with the next...") might be slightly verbose, but it is standard and unambiguous.
</RISK>
