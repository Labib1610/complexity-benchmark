The problem asks us to find the lexicographically smallest triplet of workers $(a, b, c)$ such that $1 \le a < b < c \le n$ and there are restrictions (edges in a graph) between $(a, b)$, $(a, c)$, and $(b, c)$. This is equivalent to finding the lexicographically smallest triangle (3-clique) in a graph given by its edges. We are guaranteed that at least one such triangle exists.

The constraints are $n \le 2000$ and $m \le 2 \cdot 10^5$. A brute-force check of all triplets would take $O(n^3)$ time, which is around $8 \cdot 10^9$ operations, too slow for a 2-second time limit. We need a more efficient approach.

Let's represent the graph using an adjacency list or adjacency matrix. Since $n$ is up to 2000, an adjacency matrix of size $2000 \times 2000$ is feasible (4 million integers/booleans, approx 16-32 MB), and allows $O(1)$ edge lookups. However, since $m$ is relatively small ($2 \cdot 10^5$), an adjacency list is also space-efficient.

We want to find the lexicographically smallest triangle $(a, b, c)$ with $a < b < c$.
This means we should iterate $a$ from $1$ to $n$. For a fixed $a$, we should iterate $b$ from $a+1$ to $n$. Then, we check if there exists a $c > b$ such that edges $(a, b)$, $(b, c)$, and $(a, c)$ exist.

To optimize this:
1. Iterate $a$ from $1$ to $n$.
2. Iterate $b$ in the neighbors of $a$ such that $b > a$.
3. Check if there is a common neighbor $c$ of $a$ and $b$ such that $c > b$.
4. Among all such valid $c$'s for the current pair $(a, b)$, we want the smallest one. If we find one, that triplet $(a, b, c)$ is a candidate. Since we iterate $a$ then $b$ in increasing order, the first triplet we find will be the lexicographically smallest one.

However, just checking neighbors might still be slow if the graph is dense. But $m$ is limited.
