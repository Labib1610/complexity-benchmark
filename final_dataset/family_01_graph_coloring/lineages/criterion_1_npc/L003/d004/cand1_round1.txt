<STATEMENT>
# Acoustic Levitation Arrays

Time limit: 2 s   Memory limit: 256 MB

You are tasked with tuning an acoustic levitation array consisting of $n$ wave emitters. The acoustic chamber is equipped with a maximum of 40 mounting slots, so the number of emitters will never exceed this capacity. For the system to function, every emitter must be assigned a phase offset. The hardware allows exactly three distinct offset modes, identified by the numeric codes 1, 2, and 3.

Due to the geometry of the system, certain pairs of emitters project sound waves that converge at shared focal points. In total, there are $m$ such pairs. When a pair of emitters targets the same focal point, their acoustic and thermal outputs interact. 

The hardware safety threshold requires that for any two emitters sharing a focal point, the sum of the squares of their assigned offset codes must be strictly greater than three times the square of the smaller of their two codes. If this threshold is not met, the focal point overheats, causing a localized pressure spike that destroys the levitated specimen. 

You must determine whether it is possible to assign a safe phase offset code to all $n$ emitters given the list of interacting pairs, such that the thermal threshold is satisfied for every shared focal point.

## Input
The first line contains two integers $n$ and $m$ — the number of emitters and the number of interacting emitter pairs ($1 \le n \le 40$, $0 \le m \le n(n-1)/2$). Emitters are indexed from $1$ to $n$.
Each of the subsequent $m$ lines provides two integers $u$ and $v$ ($1 \le u, v \le n$), specifying that emitter $u$ and emitter $v$ share a focal point.

## Output
If a safe tuning is impossible, output a single line containing NO.
If a valid tuning exists, output YES on the first line. On the second line, output $n$ space-separated integers $p_1, p_2, \dots, p_n$ (where each $p_i \in \{1, 2, 3\}$), representing the offset code assigned to emitter $i$. Any valid array configuration will be accepted.

## Example 1
Input:
```
4 5
1 2
1 3
2 3
1 4
2 4
```
Output:
```
YES
1 2 3 3
```

## Example 2
Input:
```
4 6
1 2
1 3
1 4
2 3
2 4
3 4
```
Output:
```
NO
```

<RATIONALE>
The previous versions allowed models to easily recognize the graph 3-coloring structure because the "singular matrix" and "determinant exactly zero" condition is a well-known mathematical affordance that trivially simplifies to `c_1 == c_2`. 
To defeat this pattern matching, I replaced the matrix determinant condition with a custom algebraic inequality: `p_u^2 + p_v^2 > 3 * min(p_u, p_v)^2`. For the domain {1, 2, 3}, this inequality is mathematically equivalent to `p_u != p_v`, but it lacks the standard semantic triggers of a coloring problem and requires either explicit case-by-case evaluation or careful algebraic reasoning to reduce to an inequality constraint.
</RATIONALE>
<PRESERVED_ANSWER>
The inequality `p_u^2 + p_v^2 > 3 * min(p_u, p_v)^2` evaluates to False when `p_u == p_v` (since 2x^2 > 3x^2 is false) and True for all distinct pairs from {1, 2, 3} (e.g., 1^2 + 2^2 = 5 > 3*1^2 = 3), making it logically identical to the original `p_u != p_v` constraint, thus preserving all valid configurations.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem remains exactly Graph 3-Coloring on the input graph, which is NP-complete, with no changes to the graph topology, variable domains, or solution space.
</PRESERVED_CLASS>
