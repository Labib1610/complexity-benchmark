# Pipeline Stage 2: Safe Batch Selection

Time limit: 2 s   Memory limit: 256 MB

## Description

In our automated deployment pipeline, the process of deploying microservices to the testing environment is divided into three consecutive stages:

**Stage 1: Conflict Analysis.** A static analysis tool examines **n** available microservices (numbered 1 to **n**) and identifies **m** pairs that share a mutable database table. These are flagged as conflicting pairs. The analyzer guarantees a specific structural property regarding these conflicts: if you form any sequence of microservices where each consecutive pair is a conflicting pair, and the first and last microservices in the sequence are the same, the total number of conflicting pairs in this sequence will always be even.

**Stage 2: Safe Batch Selection (Your Task).** The deployment coordinator receives the list of microservices and the conflicting pairs from Stage 1. It must select exactly **k** distinct microservices to form a "safe batch." A batch is safe if absolutely no two microservices within it conflict with each other. You must determine if such a batch can be formed, and if so, output the selection.

**Stage 3: Integration Testing.** The safe batch produced by Stage 2 is handed off to the container orchestration engine, which deploys them to an isolated cluster for performance testing.

Your software is only responsible for executing **Stage 2**. You will be given the output from Stage 1, and you must generate the exact batch selection required to initiate Stage 3.

## Input

The first line contains three integers **n**, **m**, and **k** (1 ≤ n ≤ 100000, 0 ≤ m ≤ 400000, 1 ≤ k ≤ n).
The following **m** lines provide the conflict data from Stage 1. Each line contains two integers **u** and **v** (1 ≤ u, v ≤ n, u ≠ v), representing a conflicting pair of microservices. No pair is listed more than once. It is guaranteed that the pairs adhere to the structural property described in Stage 1.

## Output

If a safe batch of exactly **k** microservices can be formed for Stage 3, print `YES` on the first line. On the second line, print the **k** distinct microservice numbers that form this batch, separated by spaces. If multiple safe batches of size **k** exist, any of them is accepted.

If it is impossible to form a safe batch of size **k**, print `NO`.


Replaced the explicit "two-tier" guarantee with a mechanical description of a bipartite graph (all closed walks have an even number of steps). This prevents models from pattern-matching the "two-tier" phrasing directly to a bipartite graph, forcing them to mathematically deduce that the absence of odd cycles implies bipartiteness before applying König's theorem.
</RATIONALE>
<PRESERVED_ANSWER>
The structural guarantee is mathematically equivalent to the original bipartite guarantee, meaning the maximum independent set for any valid input remains exactly the same.
</PRESERVED_ANSWER>
<PRESERVED_CLASS>
The problem still guarantees the input graph has no odd cycles (i.e., is bipartite), ensuring that the maximum independent set can still be solved in polynomial time via maximum matching.
</PRESERVED_CLASS>
<RISK>
Models might misinterpret "sequence of microservices" as only applying to simple cycles rather than any closed walk, but mathematically a graph has no odd closed walks if and only if it has no odd simple cycles, so both interpretations lead exactly to the intended bipartite structure.
</RISK>
