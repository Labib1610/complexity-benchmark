# Job Scheduling with Priority Constraints

Time limit: 5 s   Memory limit: 256 MB

## Description

A high-performance computing cluster needs to execute a batch of **k** computational jobs using **k** dedicated machines. This is a strictly one-to-one allocation task where every job must be assigned to exactly one machine, and every machine must receive exactly one job.

Additionally, to avoid resource deadlock in the shared memory bus, the scheduler must assign a unique priority level to each of these **k** allocations. There are **k** priority levels available (from 1 to **k**), and no two allocations can share the same priority.

Because of hardware compatibility, you cannot assign machines and priorities arbitrarily. You are provided with a manifest of **t** tested configurations. Each configuration is defined by three integers: a job **x**, a machine **y**, and a priority level **z**. This indicates that job **x** can be successfully executed on machine **y** with priority **z**.

You must determine if it is possible to schedule all **k** jobs by selecting exactly **k** configurations from the manifest such that:
- Each job from 1 to **k** is utilized in exactly one selected configuration.
- Each machine from 1 to **k** is utilized in exactly one selected configuration.
- Each priority level from 1 to **k** is utilized in exactly one selected configuration.

The cluster operates on small batch sizes, meaning the parameter **k** is at least one and at most twenty-two. The number of tested configurations **t** is non-negative and will not exceed the cube of **k**.

## Input

The first line contains two integers, **k** and **t**.
The subsequent **t** lines each contain three integers **x**, **y**, and **z** (1 ≤ x, y, z ≤ k), representing a valid configuration for job **x**, machine **y**, and priority **z**. All configurations in the input are distinct.

## Output

If a complete schedule can be formed, output `YES` on the initial line. Following this, output **k** lines, each containing three integers `x y z`, specifying the job, machine, and priority for each of the **k** assignments. The assignments may be printed in any order. If multiple valid schedules exist, providing any one complete plan is sufficient.

If it is impossible to schedule all **k** jobs under the given constraints, output `NO`.

## Examples

### Example 1

**Input**
```
2 3
1 1 1
1 2 2
2 2 2
```

**Output**
```
YES
1 1 1
2 2 2
```

### Example 2

**Input**
```
2 2
1 1 1
2 1 2
```

**Output**
```
NO
```

### Example 3

**Input**
```
1 1
1 1 1
```

**Output**
```
YES
1 1 1
```

## Note

In Example 2, both viable configurations require machine 1. Consequently, machine 2 cannot be utilized, making it impossible to form 2 complete assignments.

The problem was reframed from a textbook 3-dimensional matching scenario (left pillar, right pillar, keystone) to a 2-dimensional job-machine assignment problem with an added edge-coloring constraint (priority). This semantic shift triggers pattern-matching models to wrongly apply polynomial-time bipartite matching algorithms. Furthermore, the explicit small bounds (`1 <= k <= 22`) were removed from the input section and hidden as text ("twenty-two"), disabling automated heuristics that trigger exact-cover (DLX) solvers upon seeing small constraints.
</RATIONALE>
