<STATEMENT>
# Phase 3: Deployment Planner

Time limit: 1 s   Memory limit: 256 MB

## Description

The continuous integration pipeline for our cloud infrastructure operates in distinct phases:
1. **Manifest Aggregation**: Developers submit compatibility requirements for their microservices.
2. **Policy Compilation**: The orchestrator breaks down all requirements into a flat list of fallback rules covering the microservices. Every microservice must be deployed into exactly one of two availability zones: Zone 1 (primary) or Zone 0 (secondary).
3. **Deployment Planning (Your Task)**: Process the compiled rules and determine if there exists a global configuration—assigning exactly one zone to each microservice—so that at least one of the two endpoints named in each rule holds. If such a configuration exists, you must output it so the pipeline can proceed. Otherwise, you must halt the pipeline.
4. **Rollout Execution**: The system reads your configuration and deploys each microservice into its assigned zone.

Each rule names exactly two endpoints. An endpoint is represented by a non-zero integer. Its absolute value identifies the microservice. A positive integer means the endpoint holds if that microservice is deployed in Zone 1. A negative integer means the endpoint holds if that microservice is deployed in Zone 0.

## Input
The first line contains two integers $n$ and $m$. The system registry dictates the limits for $n$: there is always at least one microservice, and the registry can hold a maximum of one hundred thousand microservices. The orchestrator's limits for $m$ are bounded from below by zero, and bounded from above by exactly twice the maximum registry capacity.

Each of the following $m$ lines provides a rule as two non-zero integers $l_1$ and $l_2$. The absolute value of each integer identifies a valid microservice (from $1$ to $n$).

## Output
If no valid global configuration exists, print a single line containing `NO`.
Otherwise, print `YES` on the first line. On the second line, print $n$ integers $s_1, s_2, \dots, s_n$ separated by spaces. Print $s_i = 1$ if microservice $i$ is assigned to Zone 1, and $s_i = 0$ if it is assigned to Zone 0.

## Example 1
Input:
```
2 2
1 2
-1 -2
```
Output:
```
YES
1 0
```

## Example 2
Input:
```
1 2
1 1
-1 -1
```
Output:
```
NO
```

## Note
Multiple valid configurations may exist; any one is accepted. The same microservice ID may appear in multiple rules, and a single rule may even name the same microservice twice.

The explicit 2-SAT terminology ("acceptable service states", "required state") was removed. Instead, the problem is framed around deploying microservices into one of two availability zones, and rules name "endpoints" (a specific microservice in a specific zone) where at least one must hold. The numeric bounds for $n$ and $m$ are now stated indirectly through system registry and orchestrator capacities, forcing the reader to parse the text to extract $1 \le n \le 10^5$ and $0 \le m \le 2 \cdot 10^5$. The banned word "matching" from the previous attempt was removed.
</RATIONALE>
